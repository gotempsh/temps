# PostgreSQL Cloud backup stress results — 2026-08-08

## Environment

- Host: Apple Silicon macOS, 32 logical CPUs, 512 GiB RAM
- Docker VM: 16 CPUs, 250.5 GiB RAM, overlayfs
- PostgreSQL/WAL-G image: `gotempsh/postgres-walg:18-bookworm`
- Object storage: `rustfs/rustfs:1.0.0-beta.9`
- WAL-G tar partition threshold: 128 MiB

The generated table used exact, contiguous bigint IDs and a deterministic
384-byte payload. Every restore ran in a new empty Docker volume and verified
`count(*)`, `min(id)`, and `max(id)`.

Both checkpoints reported `object_store_grew_while_source_running=1`.
Timestamped samples show the RustFS repository increasing throughout each
live `wal-g backup-push`. Peak combined use of `/tmp` and `/var/tmp` inside the
PostgreSQL container was 8,192 bytes for both checkpoints. WAL-G used about
152 MiB RSS during the 200-million-row stream. No database-sized local staging
artifact was created.

The cumulative repository after the second run was 34,415,986,355 bytes. That
includes both base backups and the WAL segments archived while the fixture was
grown from 100 million to 200 million rows.

## Resume and outage evidence

The following deterministic tests passed:

- `temps-backup-core`: 5 executor tests. A transient engine fails three times,
  cleans up each failed attempt, waits 30, 60, and 120 seconds under Tokio's
  paused clock, and succeeds on attempt four. Permanent errors run once.
- `temps-cloud-client`: 38 tests. The upload server consumes the first chunk
  of an 8 MiB request and returns 503; the client reopens the source, reuses the
  same backup ID, streams all bytes, and also recovers lost target and
  completion responses.
- `temps-cloud`: 10 mirror tests. Repeated Cloud failures back off from 30
  seconds to a 15-minute cap; progress resets the delay.
- `temps-app-backups`: the Cloud backend re-declares a two-object snapshot
  after simulated process loss, returns `upload_required=false` for the
  committed object, and requests only the missing object.

Resume granularity is deliberately explicit: completed WAL-G repository
objects resume without retransmission. If a connection dies inside one object,
that object is reopened and retransmitted. With the 128 MiB partition threshold
the replay is bounded. WAL-G itself starts a new base-backup identity when an
entire `backup-push` process is restarted; it does not byte-resume that base
backup.

## Failure found during the run

RustFS `1.0.0-alpha.98` marked its only disk offline during the first 47.8 GB
stream at roughly 17.4 GB stored, despite 1.6 TiB free and 94% free inodes.
WAL-G then received `NoSuchBucket`/storage errors and PostgreSQL reported WAL
archive failures. The benchmark was stopped without deleting the PostgreSQL
fixture, the failed RustFS volume was replaced, and the run resumed on
`1.0.0-beta.9`. Beta.9 completed both backups and both fresh-volume restores,
and remained healthy after 34.4 GB of repository data.

Raw reports and timestamped stream samples for this run were written to
`/tmp/temps-backup-bench-100m-200m-beta9` on the benchmark host.
