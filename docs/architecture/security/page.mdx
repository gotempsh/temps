# Security Features

Temps provides defence-in-depth security across transport, access control, authentication, and application layers. This page describes what is built in and how to configure it. {{ className: 'lead' }}

---

## Transport security {{ anchor: true, id: 'transport-security' }}

### Automatic TLS with Let's Encrypt

Every domain you add to Temps gets a free TLS certificate from Let's Encrypt, issued automatically and renewed before expiration. The proxy (Pingora) terminates TLS and enforces:

- **TLS 1.2 minimum**, TLS 1.3 preferred
- **Automatic HTTP→HTTPS redirect** on port 80
- Optional **HSTS** (`Strict-Transport-Security`) and other response headers, configurable per project (see [Security headers](#security-headers) below)

You do not need to manage certificates manually. Point your domain at your server, add it in the Temps dashboard, and TLS is provisioned within seconds via the ACME protocol.

### Admin listener isolation

The Temps control plane can split its HTTP surface across two listeners so admin and management routes bind to a private interface while public ingest endpoints stay reachable over the internet. This means the dashboard and API are never exposed to public traffic unless you explicitly route them that way.

See the [Admin Listener](/docs/admin-listener) guide for configuration details, including SSH tunnel, Tailscale, and reverse-proxy deployment recipes.

## Access control {{ anchor: true, id: 'access-control' }}

### IP allow lists

Restrict access to a project's environments to specific IP addresses or CIDR ranges. Any request from an address outside the allow list is rejected at the proxy layer before it reaches your application.

Configure per project in **Settings > Security > IP Restrictions**. Changes take effect immediately without restarting containers.

### IP deny lists

Block specific IP addresses or CIDR ranges outright. Useful for blocking known attackers or geographic regions. Deny-list entries are evaluated before allow-list entries — a denied address is always rejected, even if it also appears in the allow list.

## Bot protection {{ anchor: true, id: 'bot-protection' }}

Temps includes a CAPTCHA challenge layer that can be enabled per project. When a request is flagged as suspicious, the proxy intercepts it and presents a CAPTCHA before forwarding to your application.

**When the challenge triggers:**

- High request rates from a single IP (configurable threshold)
- Traffic patterns that match known bot signatures
- Manual activation — enable for any project at any time from the dashboard

**Session-based:** a user who solves the CAPTCHA is not challenged again for the duration of their session. Legitimate users typically see the challenge once per day at most.

Enable via **Settings > Security > Bot Protection** or through the [Attack Mode](/docs/attack-mode) feature for a full lockdown.

## Authentication {{ anchor: true, id: 'authentication' }}

Temps supports multiple authentication methods for the dashboard and API:

| Method | Description |
|--------|-------------|
| **Email + password** | Standard login with Argon2-hashed passwords. Password reset via email. |
| **Passwordless / magic link** | A time-limited login link is emailed to the user. No password to remember or leak. |
| **TOTP (2FA)** | Time-based one-time passwords via any authenticator app (Google Authenticator, Authy, 1Password). Can be made mandatory for Admin users. |
| **OIDC / SSO** | OpenID Connect for enterprise identity providers (Okta, Azure AD, Google Workspace, Keycloak). Users are provisioned on first login. |
| **API keys** | Long-lived tokens for programmatic access. Scoped to specific permissions. See [Manage Team Access](/docs/manage-team-access). |
| **CLI device flow** | OAuth 2.0 Device Authorization Grant. The CLI displays a code; you approve in your browser. Credentials are never typed into the terminal. |

### Account security defaults

- Passwords are stored as Argon2 hashes — the plaintext is never persisted.
- Sessions expire and tokens have configurable lifetimes.
- Rate limiting is applied to login endpoints to prevent brute-force attacks.
- MFA recovery codes are generated at enrollment and stored encrypted.

## Role-based access control {{ anchor: true, id: 'rbac' }}

Every request to the Temps API is evaluated against the requesting user's role. Temps ships with six built-in roles:

| Role | Access level |
|------|-------------|
| **Admin** | Full platform access, including user management and system settings |
| **User** | Create and manage projects, deploy, manage env vars and domains. Cannot manage users or system settings. |
| **Reader** | Read-only access to all resources |
| **ApiReader** | Read-only API access (projects, deployments, analytics) |
| **Mcp** | MCP server access — deploy and manage projects via the Model Context Protocol |
| **Custom** | No default permissions. Used for API keys where you grant only the permissions needed. |

Permissions follow the `resource:action` pattern (e.g. `deployments:create`, `logs:read`, `users:write`). API keys with the **Custom** role can be granted any subset of the 80+ defined permissions.

See [Teams & Collaboration](/docs/teams) for the full permissions matrix and instructions for creating users and API keys.

## Data protection {{ anchor: true, id: 'data-protection' }}

### Encryption at rest

Sensitive values stored in the database are encrypted before persistence:

- Environment variable values (secrets)
- TLS certificate private keys
- API key hashes (keys are shown only once at creation)
- MFA secrets and recovery codes

Passwords are hashed (Argon2id), not encrypted — the plaintext is never recoverable.

### Encryption in transit

All traffic between clients and Temps is encrypted with TLS. Internal service-to-service communication (control plane to worker nodes) uses mutual TLS when WireGuard is not in use.

## Security headers {{ anchor: true, id: 'security-headers' }}

The Pingora proxy can add the following security headers to responses. None are sent by default — each is opt-in and configured per project under **Environment Settings → Security Headers**. Leave a field blank to skip the header for that project.

| Header | Example value | Purpose |
|--------|--------------|---------|
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | Force HTTPS for one year |
| `X-Frame-Options` | `SAMEORIGIN` | Prevent clickjacking via iframes |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Limit referrer leakage |
| `Content-Security-Policy` | `default-src 'self'` | Restrict resource origins |

Set the headers your application actually needs — there is no project-wide default that you can rely on.

## Monitoring and audit log {{ anchor: true, id: 'monitoring-audit-log' }}

### Audit log

Every action performed through the dashboard or API is recorded. Each entry captures the user, operation type, IP address (with geolocation), timestamp, and a JSON payload with the affected resource.

Recorded events include:

- User logins, logouts, and failed authentication attempts
- Role changes and user creation/deletion
- API key creation and revocation
- Deployment creation, cancellation, and rollback
- Environment variable changes
- Domain additions and removals
- System setting changes

Access the audit log at **Settings > Audit Log**. Users with the `audit:read` permission (Admin and User roles) can view entries.

### Uptime and health monitoring

Use [Monitoring](/docs/monitoring) to set up HTTP health checks for your applications. Monitors alert you when an endpoint becomes unreachable and track uptime over time.

## Best practices {{ anchor: true, id: 'best-practices' }}

<Properties>
  <Property name="Enable 2FA for Admin accounts">
    Require TOTP for all users with the Admin role. A compromised admin account grants full platform access.
  </Property>
  <Property name="Use IP allow lists for internal tools">
    If a project is only accessed from your office or VPN, add an IP allow list. This eliminates exposure to the public internet entirely.
  </Property>
  <Property name="Use scoped API keys">
    Create one API key per integration with only the permissions that integration needs. Revoke keys that are no longer in use.
  </Property>
  <Property name="Bind the admin listener to a private interface">
    Use the `TEMPS_CONSOLE_ADMIN_ADDRESS` flag to expose the dashboard only on a private network interface or loopback. Combine with an SSH tunnel or VPN for remote access.
  </Property>
  <Property name="Review the audit log regularly">
    Check for unexpected logins, role changes, or deployments — especially after team changes or security incidents.
  </Property>
  <Property name="Keep Temps updated">
    New releases fix security issues. Subscribe to GitHub releases or the changelog to stay current.
  </Property>
</Properties>

## Reporting security issues {{ anchor: true, id: 'reporting-security-issues' }}

If you discover a security vulnerability in Temps, please report it privately before public disclosure. This gives the team time to investigate and release a fix.

**Contact:** security@temps.sh

Please include a description of the vulnerability, steps to reproduce, and the potential impact. We aim to acknowledge reports within 48 hours and release a fix within 14 days for critical issues.
