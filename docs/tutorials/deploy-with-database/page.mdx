# Deploy with a Database

This tutorial walks you through provisioning a managed PostgreSQL database on Temps, connecting it to your application, and deploying. No external database providers, no connection string juggling — Temps runs the database on your server and wires everything together automatically. {{ className: 'lead' }}

---

## What you will build {{ anchor: true, id: 'what-you-will-build' }}

By the end of this tutorial, you will have:

- A managed PostgreSQL database running as a Docker container on your server
- The database linked to your project with environment variables injected automatically
- An application deployed and connected to the database
- A Redis cache added as a bonus second service
- Knowledge of how Temps manages per-environment database isolation

**Time required:** approximately 15 minutes.

**What this tutorial covers and does not cover:**

| Covered | Not covered |
|---------|-------------|
| Provisioning PostgreSQL and Redis | MongoDB and S3 storage (same process, different service type) |
| Linking services to projects | Database migrations and schema management |
| Automatic environment variable injection | Connection pooling and performance tuning |
| Per-environment database isolation | Replication and high availability |
| Querying data from the dashboard | Backup and restore ([previous tutorial](/docs/set-up-backups-and-monitoring)) |

---

## Prerequisites {{ anchor: true, id: 'prerequisites' }}

You need:

- A **running Temps instance** with a deployed project (complete [Your First Deployment](/docs/your-first-deployment) first)
- An **application that uses a database** — any framework that reads a database connection string from an environment variable will work. This tutorial shows examples for Next.js, Express, and generic Node.js.

If your current project does not use a database, that is fine. You can still follow along to provision the service and link it — then add database code later.

## Create a PostgreSQL service {{ anchor: true, id: 'create-a-postgresql-service' }}

A managed service in Temps is a Docker container that Temps provisions, monitors, and backs up for you. You create the service once and then link it to any number of projects.

<AgentPath
  title="Create a PostgreSQL service"
  instruction="Create a managed PostgreSQL service named my-app-db on my Temps instance."
  command="bunx @temps-sdk/cli services create -t postgres -n my-app-db -y"
  verify="bunx @temps-sdk/cli services list"
  dashboard={[
    "In the sidebar, under Data, click Databases, then click Create database.",
    "Select PostgreSQL as the service type.",
    "Give it a unique name, e.g. my-app-db (this becomes the Docker container name postgres-my-app-db).",
    {
      text: "Adjust parameters if needed (host port auto-assigned from 5432 and bound to 127.0.0.1, Docker image gotempsh/postgres-walg:18-bookworm, max connections 100), then click Create database. Temps pulls the image, creates the container and volume, and runs the pg_isready health check.",
      verify: "Wait until the service status shows Running on the Databases page -- that confirms the database is ready.",
    },
  ]}
/>

1. In the sidebar, under **Data**, click **Databases**
2. Click **Create database**
3. Select **PostgreSQL** as the service type
4. Configure it:

<Properties>
  <Property name="Name">
    A unique name for this service, e.g. `my-app-db`. This becomes part of the Docker container name (`postgres-my-app-db`) and the volume name.
  </Property>
  <Property name="Parameters">
    Temps auto-fills sensible defaults. You can adjust:

    - **Port** — The host port to bind. Auto-assigned starting from 5432. Bound to `127.0.0.1` only (not publicly accessible).
    - **Docker Image** — Default: `gotempsh/postgres-walg:18-bookworm` (PostgreSQL 18 with WAL-G for streaming backups). You can also use `timescale/timescaledb-ha:pg18` if you need TimescaleDB.
    - **Max Connections** — Default: `100`. Increase for high-concurrency applications.

    Fields that are auto-generated and read-only after creation:
    - **Database** — `postgres` (the root database; per-project databases are created automatically when linked — CLI defaults the root database to `myapp`)
    - **Username** — `postgres`
    - **Password** — A random 16-character alphanumeric string, encrypted at rest
  </Property>
</Properties>

Click **Create database**. Temps pulls the Docker image (if not cached), creates a container and a persistent volume, starts the service, and waits for the health check (`pg_isready`) to pass.

When the status shows **Running**, your database is ready.

<Note>
**Where does data live?** PostgreSQL data is stored in a Docker volume named `postgres-{service-name}_data`, mounted at `/var/lib/postgresql` inside the container. The volume persists across container restarts and Temps upgrades. Back it up with the [backup system](/docs/set-up-backups-and-monitoring) for off-site protection.
</Note>

## Link the service to your project {{ anchor: true, id: 'link-the-service-to-your-project' }}

Creating a service does not automatically connect it to any project. You need to explicitly link them.

<AgentPath
  title="Link the service to your project"
  instruction="Link the PostgreSQL service my-app-db to my project my-app so the connection details get injected at deploy time."
  command="bunx @temps-sdk/cli services link --id <service-id> -p my-app"
  verify="bunx @temps-sdk/cli services projects --id <service-id>"
  dashboard={[
    "Open your project in the dashboard and click Databases in the project sidebar.",
    "Under Link an existing database, find the PostgreSQL service you just created.",
    {
      text: "Click Link on its row. On the next deploy, Temps creates a dedicated my_app_production database and injects the connection details as environment variables.",
      verify: "Confirm the service now shows a Browse button instead of Link on your project's Databases page.",
    },
  ]}
/>

<Note>
Find `<service-id>` in the ID column of `bunx @temps-sdk/cli services list`.
</Note>

1. Open your project in the dashboard
2. Click **Databases** in the project sidebar
3. Under **Link an existing database**, find the PostgreSQL service you just created
4. Click **Link** on its row

That is it. The next time your project deploys, Temps will inject the database connection details as environment variables into your application container.

### What linking does under the hood

When you link a PostgreSQL service to a project, Temps:

1. Creates a **dedicated database** inside the PostgreSQL instance named `{project_slug}_{environment_slug}` (e.g. `my_app_production`). Each project-environment combination gets its own isolated database.
2. Generates **environment variables** with the connection details, using the Docker container name as the hostname (so containers can talk to each other over the Docker network).
3. Stores the link in a `project_services` table — only one service of each type can be linked per project.

<Note>
**One service, many projects:** A single PostgreSQL service can be linked to multiple projects. Each project gets its own database inside the same PostgreSQL instance. This is efficient for a single server — you run one PostgreSQL container instead of one per project.
</Note>

## Understand the injected environment variables {{ anchor: true, id: 'understand-the-injected-environment-variables' }}

When a PostgreSQL service is linked to your project, Temps injects these environment variables at deploy time:

<Properties>
  <Property name="POSTGRES_URL">
    The full connection string: `postgresql://postgres:PASSWORD@postgres-SERVICE-NAME:5432/PROJECT_ENV_DB`

    The hostname is the Docker container name (e.g. `postgres-my-app-db`), the port is always `5432` (the internal port, not the host-mapped port), and the database name is your project-environment combination.
  </Property>
  <Property name="POSTGRES_HOST">
    The container hostname: `postgres-my-app-db`
  </Property>
  <Property name="POSTGRES_PORT">
    The internal port: `5432`
  </Property>
  <Property name="POSTGRES_DB">
    The per-project database name: `my_app_production`. The same value is also injected as `POSTGRES_DATABASE` and `POSTGRES_NAME`.
  </Property>
  <Property name="POSTGRES_USER">
    The username: `postgres`
  </Property>
  <Property name="POSTGRES_PASSWORD">
    The auto-generated password.
  </Property>
</Properties>

### Preview before deploying

To see which variables the link provides without deploying, run:

```bash
bunx @temps-sdk/cli services env --id <service-id> -p my-app
```

It lists the variable names with masked values. The per-environment database name is filled in at deploy time.

### Common framework mappings

Many frameworks read `DATABASE_URL` rather than `POSTGRES_URL`, and Temps doesn't inject `DATABASE_URL` for PostgreSQL. Point your app at `POSTGRES_URL` instead:

```typescript
// Before
const db = new Pool({ connectionString: process.env.DATABASE_URL });

// After
const db = new Pool({ connectionString: process.env.POSTGRES_URL });
```

<Note>
Don't set `DATABASE_URL` to `$POSTGRES_URL` in your environment variables. Temps doesn't expand references to other variables, so your app would receive the literal text `$POSTGRES_URL`.
</Note>

## Update your application {{ anchor: true, id: 'update-your-application' }}

Add database access to your application. Below are examples for common frameworks. The key point: read the connection string from `POSTGRES_URL`.

<CodeGroup title="Connect to PostgreSQL">

```typescript {{ title: 'Next.js / Drizzle' }}
// db/index.ts
import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';

const pool = new Pool({
  connectionString: process.env.POSTGRES_URL,
});

export const db = drizzle(pool);
```

```typescript {{ title: 'Next.js / Prisma' }}
// prisma/schema.prisma
datasource db {
  provider = "postgresql"
  url      = env("POSTGRES_URL")
}

// Then generate and push schema:
// npx prisma generate
// npx prisma db push
```

```typescript {{ title: 'Express / pg' }}
// server.ts
import express from 'express';
import { Pool } from 'pg';

const pool = new Pool({
  connectionString: process.env.POSTGRES_URL,
});

const app = express();

app.get('/health', async (req, res) => {
  const result = await pool.query('SELECT NOW()');
  res.json({ status: 'ok', time: result.rows[0].now });
});

app.listen(3000);
```

```python {{ title: 'Flask / SQLAlchemy' }}
# app.py
import os
from flask import Flask
from flask_sqlalchemy import SQLAlchemy

app = Flask(__name__)
app.config['SQLALCHEMY_DATABASE_URI'] = os.environ['POSTGRES_URL']
db = SQLAlchemy(app)
```

</CodeGroup>

### Add a health check that verifies database connectivity

A good health endpoint confirms the database is reachable:

```typescript {{ title: 'api/health/route.ts (Next.js App Router)' }}
import { Pool } from 'pg';
import { NextResponse } from 'next/server';

const pool = new Pool({
  connectionString: process.env.POSTGRES_URL,
});

export async function GET() {
  try {
    await pool.query('SELECT 1');
    return NextResponse.json({ status: 'ok', database: 'connected' });
  } catch (error) {
    return NextResponse.json(
      { status: 'error', database: 'disconnected' },
      { status: 500 }
    );
  }
}
```

This gives your [uptime monitor](/docs/set-up-backups-and-monitoring#create-an-uptime-monitor) a way to detect database outages, not just application crashes.

## Deploy and verify {{ anchor: true, id: 'deploy-and-verify' }}

Commit your changes and push:

```bash
git add .
git commit -m "feat: add PostgreSQL database connection"
git push
```

Temps detects the push, builds your application, and deploys it. This time, the deploy includes the database environment variables.

2. Confirm you see `"database": "connected"` in the response

### Troubleshooting

If your application fails to connect to the database:

<Properties>
  <Property name="Connection refused">
    Your app is trying to connect to `localhost` instead of the container name. Make sure you are reading `POSTGRES_URL` (which uses the Docker container hostname) rather than hardcoding `localhost`.
  </Property>
  <Property name="Database does not exist">
    Temps creates the per-project database on first deploy. If you linked the service after the last deploy, trigger a new deployment (push a commit or use the **Redeploy** button).
  </Property>
  <Property name="Authentication failed">
    The password in `POSTGRES_URL` is auto-generated. Do not set the password manually in your environment variables — let Temps inject it.
  </Property>
  <Property name="Timeout connecting">
    Check that the PostgreSQL service is running. Go to **Databases** in the sidebar, open the service and verify the status is **Running**. If it is stopped, click **Start**.
  </Property>
</Properties>

## Explore your data {{ anchor: true, id: 'explore-your-data' }}

Temps includes a built-in data browser that lets you explore and query your databases directly from the dashboard without installing any tools.

1. Open your project in the dashboard
2. Click **Databases** in the project sidebar
3. Click **Browse** on your linked PostgreSQL service
4. Browse the tables, or type SQL into the command bar to run it

```sql
-- See all tables
SELECT tablename FROM pg_tables WHERE schemaname = 'public';

-- Check your data
SELECT * FROM users LIMIT 10;

-- Database size
SELECT pg_size_pretty(pg_database_size(current_database()));
```

This is useful for quick debugging and data inspection. For ongoing database management, connect with your preferred client (pgAdmin, DBeaver, TablePlus) using the host port shown on the service details page:

```bash
# Connect from your local machine (requires SSH tunnel or direct access)
psql "postgres://postgres:PASSWORD@your-server-ip:PORT/my_app_production"
```

<Note>
**Security:** The PostgreSQL port is bound to `127.0.0.1` on the server, meaning it is not publicly accessible. To connect from your local machine, use an SSH tunnel: `ssh -L 5432:localhost:PORT user@your-server-ip`, then connect to `localhost:5432`.
</Note>

## What you have accomplished {{ anchor: true, id: 'what-you-have-accomplished' }}

You now have a complete data stack running on your server:

| Service | Container | Purpose |
|---------|-----------|---------|
| PostgreSQL | `postgres-my-app-db` | Primary database with per-environment isolation |
| Redis | `redis-my-app-cache` | Caching and session storage |

Key concepts you learned:

- **Services are shared:** One PostgreSQL instance can serve multiple projects, each getting its own database
- **Environment isolation:** Temps creates `{project}_{environment}` databases automatically, so production and staging data never mix
- **Automatic wiring:** Link a service to a project and Temps handles the environment variables, networking, and database creation
- **Docker networking:** Containers communicate using Docker container names as hostnames over an internal network. The database port is only exposed to `127.0.0.1` on the host.

### Available service types

The same workflow applies to all managed services:

| Service | Default Image | Environment Variables |
|---------|--------------|----------------------|
| PostgreSQL | `gotempsh/postgres-walg:18-bookworm` | `POSTGRES_URL`, `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB` (also `POSTGRES_DATABASE`, `POSTGRES_NAME`), `POSTGRES_USER`, `POSTGRES_PASSWORD` |
| Redis | `gotempsh/redis-walg:8-bookworm` | `REDIS_URL`, `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `REDIS_DATABASE` |
| MongoDB | `gotempsh/mongodb-walg:8.0` | `MONGODB_URL`, `MONGODB_HOST`, `MONGODB_PORT`, `MONGODB_DATABASE`, `MONGODB_USERNAME`, `MONGODB_PASSWORD` |
| S3 Storage | `rustfs/rustfs:1.0.0` | `S3_BUCKET`, `S3_ENDPOINT`, `S3_HOST`, `S3_PORT`, `S3_REGION`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`, `AWS_ENDPOINT_URL` |
