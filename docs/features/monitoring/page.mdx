# Monitoring

Monitor your application's health, performance, and resource usage in real-time. Get visibility into CPU, memory, network traffic, and response times to proactively detect and resolve issues. {{ className: 'lead' }}

---

## Real-Time Metrics

Temps provides real-time metrics for every deployed container, giving you instant visibility into your application's performance.

<Row>
  <Col>
    **Available Metrics:**
    - **Requests** - Total requests and request rate
    - **Response Time** - Average response time in ms
    - **CPU Usage** - Percentage of CPU resources used
    - **Memory Usage** - RAM consumption in MB and percentage
    - **Network I/O** - Inbound and outbound data transfer rate

    Metrics update in real-time, so you always see current performance data.

  </Col>
  <Col>
    **Where to View:**
    1. Navigate to your project in the dashboard
    2. Open the **Monitoring** tab
    3. View real-time metrics and charts
  </Col>
</Row>

---

## Accessing Metrics

### Via Dashboard

1. Go to **Projects** → Select your project
2. Click the **Monitoring** tab
3. View real-time metrics: requests, response time, CPU, memory, and network I/O

The monitoring dashboard shows:

- **Requests** - Total requests over time with request rate
- **Response Time** - Average response time graph
- **CPU** - Live CPU usage percentage
- **Memory** - Live memory usage in MB and percentage
- **Network I/O** - Real-time inbound/outbound data transfer

### Via API

Access metrics programmatically using the API:

```bash
# Get real-time metrics for an environment
curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/environments/{environment_id}/metrics"
```

The API returns:

```json
{
  "requests_total": 1523,
  "requests_rate": 12.5,
  "response_time_avg_ms": 45,
  "cpu_percent": 23.5,
  "memory_bytes": 268435456,
  "memory_percent": 52.0,
  "network_rx_bytes_per_sec": 1024,
  "network_tx_bytes_per_sec": 2048
}
```

## Understanding Metrics

<Properties>
  <Property name="Requests">
    Total number of HTTP requests and the current request rate. Use this to
    understand your traffic volume and spot sudden spikes or drops.

    **Investigate when:** request rate spikes unexpectedly, or drops to zero
    (possible outage).
  </Property>

  <Property name="Response Time">
    Average time to process a request, in milliseconds. A healthy web application
    typically responds in under 200 ms for API calls and under 500 ms for
    server-rendered pages.

    **Investigate when:** average response time climbs above 500 ms consistently.
    Common causes: slow database queries, missing indexes, or insufficient CPU.
  </Property>

  <Property name="CPU Usage">
    Percentage of the CPU allocation your container is using. Occasional spikes
    above 90% during traffic bursts are normal. Sustained high CPU means the
    container is throttled and requests are queuing.

    **Investigate when:** CPU stays above 80% for more than a few minutes. Either
    increase the CPU limit in project settings or profile the application for
    hot paths.
  </Property>

  <Property name="Memory Usage">
    RAM consumption in bytes and as a percentage of the memory limit. When a
    container exceeds its limit Docker kills it (OOM kill) and Temps restarts it
    automatically.

    **Investigate when:** memory is above 85% of the limit, or usage grows
    steadily over time (memory leak). Increase the limit or profile the
    application with a heap dump.
  </Property>

  <Property name="Network I/O">
    Inbound and outbound data transfer in bytes per second. High outbound traffic
    is normal for media-heavy applications. Sudden massive spikes in either
    direction can indicate a DDoS attack or runaway polling loop.

    **Investigate when:** outbound traffic spikes without a matching increase in
    requests (possible data exfiltration or misconfigured client).
  </Property>
</Properties>

## Health Checks

Configure health checks to automatically monitor your application's availability:

### Setting Up Health Checks

Health checks are configured in your project's deployment settings:

1. Go to **Project Settings** → **Deployment**
2. Configure **Health Check** settings:
   - **Path:** Endpoint to check (e.g., `/health` or `/api/health`)
   - **Interval:** How often to check (default: 30 seconds)
   - **Timeout:** Maximum wait time (default: 5 seconds)
   - **Retries:** Number of failed attempts before marking unhealthy

### Health Check Endpoint

Your application should expose a health check endpoint that returns quickly:

```javascript
// Express.js example
app.get("/health", (req, res) => {
  res.status(200).json({ status: "ok", timestamp: Date.now() });
});
```

```python
# Flask example
@app.route('/health')
def health():
    return {'status': 'ok', 'timestamp': time.time()}, 200
```

<Note>
  **Best Practice:** Keep health checks lightweight. They should check basic
  application state (database connectivity, critical services) but avoid
  expensive operations.
</Note>

## Monitoring Best Practices

<Properties>
  <Property name="Set Resource Limits">
    Configure explicit CPU and memory limits so one container cannot starve
    others. Start with the defaults, deploy, then check actual usage after a day
    of real traffic. Adjust the limits to leave a 20–30 % headroom above peak.

    **Where to set:** Project Settings → Deployment → Resources.
  </Property>

  <Property name="Watch Trends, Not Just Snapshots">
    Spot-checking a single value tells you little. Look at 1-hour and 24-hour
    graphs to identify: gradual memory growth (memory leak), CPU spikes at the
    same time each day (scheduled jobs), or network anomalies (security events).
  </Property>

  <Property name="Set Up Alerts Early">
    Configure alerts before you have an incident, not during one. Recommended
    thresholds to start with:

    - CPU above 90% for 5 consecutive minutes
    - Memory above 85% of the allocation
    - Container restarts (any)
    - Health check failures

    Alerts can be delivered via email, webhooks, or Slack integrations.
  </Property>

  <Property name="Compare Environments">
    Run the same workload on staging and production and compare the resource
    graphs side by side. Unexpectedly higher CPU or memory in production
    typically reveals a configuration difference (missing cache, more replicas,
    larger dataset) rather than a code bug.
  </Property>
</Properties>

## Troubleshooting

<Properties>
  <Property name="High CPU Usage">
    **Symptoms:** CPU graph consistently above 80–90 %.

    **Possible causes:** inefficient algorithms, too many concurrent requests,
    or insufficient CPU allocation.

    **Solutions:**
    1. Increase the CPU limit in Project Settings → Deployment → Resources
    2. Optimize hot code paths (profile with `perf`, `py-spy`, or your
       language's built-in profiler)
    3. Add caching (Redis, in-memory) to reduce repeated computation
    4. Scale horizontally by increasing the replica count
  </Property>

  <Property name="High Memory Usage">
    **Symptoms:** Memory approaching the allocation limit, or container
    restarting with OOM errors.

    **Possible causes:** memory leaks, insufficient allocation, or large
    in-memory data structures.

    **Solutions:**
    1. Increase the memory limit in project settings
    2. Profile the application for leaks (heap dump, `valgrind`, etc.)
    3. Add pagination for large dataset queries
    4. Use streaming for large file reads and writes
  </Property>

  <Property name="Container Restarts">
    **Symptoms:** Container restart counter increasing; logs show `OOMKilled` or
    an unhandled exception at exit.

    **Solutions:**
    1. Open the deployment logs and search for the last error before the restart
    2. Check the memory graph — a usage spike right before each restart points
       to OOM; increase the memory limit
    3. Verify the health check endpoint responds within the configured timeout
    4. Fix any unhandled exceptions logged at shutdown
  </Property>

  <Property name="Metrics Not Updating">
    **Symptoms:** Monitoring dashboard shows stale values or a "no data"
    message.

    **Solutions:**
    1. Confirm a deployment is in the `ready` or `deployed` state — metrics
       only stream from running containers
    2. Hard-refresh the dashboard (Ctrl+Shift+R) to reconnect the SSE stream
    3. Check that the container is not in a crash-restart loop (rapid restarts
       disconnect the metric stream)
  </Property>
</Properties>
