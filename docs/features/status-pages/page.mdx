# Status Pages

A status page shows your users whether your services are up, without giving them access to Temps. You pick which uptime monitors appear — from any of your projects — what they are called and how they are grouped; Temps publishes their current state, 90 days of daily uptime and the incident updates you mark as public, at an unguessable link. {{ className: 'lead' }}

Status pages are **Beta**. See [feature maturity](/docs/feature-maturity).

---

## What a visitor sees

- A banner with the overall state: all operational, degraded, or down.
- One row per selected monitor, under the **public name** you gave it, with its current state, uptime over 90 days and a bar per day. Components that share a **group** (for example `Cloud` → API, Dashboard, Billing) are shown together under one collapsible row with the group's worst state; it opens by itself when something in it is not operational.
- Active and recently resolved (last 14 days) incidents, showing only the updates you made public.

The page is plain HTML with no JavaScript and refreshes itself every minute. The same data is available as JSON at `…/summary.json` for widgets and scripts.

### What is never published

A status page is built from an allowlist, not by hiding fields from the internal view. It never contains:

- monitor names, URLs, check paths, hostnames or IP addresses;
- probe response bodies or error messages;
- project or environment names;
- database IDs of any kind;
- an incident's internal title and description (visitors see the **Headline** you write for the incident, or, when you leave it empty, a heading based on its impact, such as "Partial outage");
- incident updates you did not make public;
- anything about monitors you did not select, or incidents tied only to them.

Timing data is published. Each component shows its uptime percentage and average response time, and the JSON carries, for every day, the number of checks run, failed and degraded. To hide it, open the page's appearance settings and use **What to show**. Switching off **Uptime percentages** also removes the per-day check counts, because they would give the percentage away. Switching off **Response times** removes the average response times and the response-time chart. The colored bars are always shown.

## Create and publish a page

1. Open **Status pages** in the sidebar (under **Observability**). A project's **Status Pages** tab lists the pages that show it and starts a new page from that project.
2. Click **Create status page** and give it a public title.
3. Add components: choose a **project** and one of its **environments**, then **Add**. Repeat for every service the page should show, from as many projects as you like. Give each a **public name** (for example `API` or `Dashboard`) and, optionally, a **group**.
4. Leave **Publish right away** on, or turn it off to create a **draft** whose link returns "not found" until you publish it.

A page is created with at least one component and cannot be published without one. You can change a component's project or environment later in its **Components** tab.

### Who can manage a page

A page is authorized against every project it draws components from: reading it needs `status_page:read` on each of them, and changing it needs the matching permission on each. Editing the components is checked against the projects before *and* after the change, so a page cannot be taken over by removing the components you have no access to, and you cannot add another team's monitor to your page. Instance administrators can manage every page. Deployment tokens cannot use the status page API.

### From the CLI

```bash
# Create a draft showing monitor 12 as "API" and monitor 15 as "Dashboard"
# (they may belong to different projects), grouped under "Cloud"
temps status-pages create --title "Acme status" \
  --monitor 12=API --monitor 15=Dashboard --group "Cloud=12,15"

temps status-pages list --project-id 3   # only pages showing project 3

temps status-pages publish --id 1
temps status-pages show --id 1        # prints the public URL
```

### From the API

| Action | Endpoint |
|---|---|
| List pages | `GET /api/status-pages` (optional `?project_id=` for the pages showing a project) |
| Create a draft | `POST /api/status-pages` |
| Read one | `GET /api/status-pages/{id}` |
| Change title, description or monitors | `PATCH /api/status-pages/{id}` |

The public view is served without authentication at `GET /api/status/{slug}` (HTML) and `GET /api/status/{slug}/summary.json` (JSON).

## Taking a page down

Each of these makes the old link return "not found" **immediately**, before the API call returns:

- **Unpublish** keeps the page and its settings as a draft.
- **Replace public link** issues a new link and retires the old one, for when a link was shared too widely.
- **Delete** removes the page.

Deleting a project or a selected monitor does not retire a page: it only removes those components. A page that still shows another project's components stays public with what is left. A page left with no components answers "not found" but keeps its link, hostnames and settings until you delete it, and it cannot be published again until you add a component. To retire a page, unpublish or delete it.

Public responses are sent with `Cache-Control: no-store`, so browsers and proxies do not keep a copy after you take the page down.

## Public incident updates

Incident updates are **private by default**. To share one:

- In the console, open a status page and use **Incident updates**: switch an existing update to **Public**, or post a new update with **Show on status pages** ticked.
- From the CLI: `temps incidents update-status --id 7 --status identified --message "…" --public`, or `temps incidents set-visibility --id 7 --update-id 31 --public`.

The automatic first update ("Incident created: …") contains the internal incident title and can never be made public.

An incident appears on a page when it has at least one public update and it concerns a monitor selected on that page, an environment one of those monitors watches, or the whole project.

## Email subscribers

Visitors can subscribe to a page by email and get a message for every public incident update and for the resolution. Nothing else is ever sent: a notice carries the incident's public heading, its public status, the public names of the affected components and the text of one public update, exactly as the page shows them. Private updates, internal titles, monitor names and errors never reach a subscriber.

### Switching it on

Open the status page, then **Subscribers**:

1. Enter a **sender address** at one of your verified email domains, for example `status@example.com`.
2. Switch **Email updates for visitors** on. The public page now ends with a subscribe form.

If something is missing, the tab says what and links to where it is fixed: **No email provider is configured** (add one under **Email**), no verified email domain, or no public URL for the links in the mails (set the external URL or public ingress URL, or attach a custom domain to the page). Subscriptions cannot be switched on until mail can actually go out.

Only updates published **after** subscriptions were switched on are announced, so switching them on never mails out the page's history.

```bash
temps status-pages subscriptions show --id 1
temps status-pages subscriptions set --id 1 --sender status@example.com --enable
temps status-pages subscriptions set --id 1 --disable
```

### What a visitor goes through

1. They enter their address in the form. The answer is the same whether the address is new, waiting for confirmation or already subscribed.
2. Temps sends a confirmation link (double opt-in). Opening it shows a **Confirm subscription** button; nothing is stored as confirmed until it is clicked, so mail scanners that open links cannot subscribe anyone. The link is valid for 48 hours and works once. A repeated request sends a new link at most every 10 minutes.
3. Every notice ends with an **Unsubscribe** link. Following it and clicking **Unsubscribe** deletes the address from the page.

Mail goes through the transactional email stack (**Email**), so its suppression list applies: an address that bounced or complained is not mailed. Mail is sent without open or click tracking.

### Subscriber data

Addresses are personal data:

- They are stored per page, shown only to people who can change the page (`status_page:write`), and never to other subscribers.
- You can delete one (**Subscribers** → the bin icon, or `temps status-pages subscribers delete --id 1 --subscriber-id 9`), export all of them as CSV (**Export CSV**, or `temps status-pages subscribers export --id 1 -o subscribers.csv`), and deleting the page deletes them all.
- An address that is never confirmed is deleted 48 hours after its last request.
- No token is stored in plaintext: only hashes of the confirmation and unsubscribe tokens are kept.
- Changing the settings, deleting a subscriber and exporting are audit-logged (`STATUS_PAGE_SUBSCRIPTIONS_UPDATED`, `STATUS_PAGE_SUBSCRIBER_DELETED`, `STATUS_PAGE_SUBSCRIBERS_EXPORTED`), without the addresses.

| Action | Endpoint |
|---|---|
| Settings | `GET /api/status-pages/{id}/subscriptions` |
| Change settings | `PUT /api/status-pages/{id}/subscriptions` |
| List subscribers | `GET /api/status-pages/{id}/subscribers` |
| Export as CSV | `GET /api/status-pages/{id}/subscribers/export` |
| Delete a subscriber | `DELETE /api/status-pages/{id}/subscribers/{subscriber_id}` |

### How notices are sent

A background task checks every 20 seconds. It queues one notice per public update published in the last 24 hours, sends pending confirmations, then delivers notices to confirmed subscribers in batches, at most 200 mails per run across all pages. A notice goes to the subscribers who had confirmed when it was queued, each at most once, also across restarts. If an update stops being public before its mail has gone out (made private, the page unpublished, subscriptions switched off), the rest of the delivery is cancelled.

## Atom feed

Every published page has an Atom feed at `/api/status/<token>/feed.atom` (or `/feed.atom` on a custom domain), linked from the page's footer and shown under **Notifications** in the console and by `temps status-pages show`, so feed readers and chat integrations can follow it. It lists the newest 50 public incident updates, resolutions and maintenance announcements, with the same text the page shows; nothing private is ever in it, and entry IDs are opaque. Like the page, it is served from memory and refreshed every minute. A password-protected page has no feed: a feed reader cannot sign in, and the feed answers "not found".

## Maintenance windows

Announce planned work ahead of time, e.g. "Database upgrade, Sunday 22:00–23:00". Open the page's **Maintenance** tab, click **Schedule maintenance**, and give it a title, a start and an end (in your browser's time zone), the components it affects and, optionally, a description.

- **Before it starts** the page lists it under "Scheduled maintenance". Subscribers and webhooks are told **once**, when you schedule it. Changing or cancelling it later updates the page but sends nothing.
- **While it runs** its components show **Under maintenance**, **outage alerts for their monitors are paused**, and checks taken during the window are **left out of uptime**, on every page that shows the monitor. Monitoring itself keeps running.
- **Once it has started** its start and components are fixed; the title, description and end can still change. **End now** cancels a running window early; checks taken until then stay out of uptime.

A window cannot be backdated (a few minutes of slack allow for "now"), lasts at most 7 days, and starts at most a year ahead. A page has at most 20 scheduled or running windows.

```bash
temps status-pages maintenance schedule --id 1 --title "Database upgrade" \
  --starts 2026-12-01T22:00:00Z --duration 1h --monitor 12 --monitor 15
temps status-pages maintenance list --id 1
temps status-pages maintenance update --id 1 --maintenance-id 4 --ends 2026-12-01T23:30:00Z
temps status-pages maintenance cancel --id 1 --maintenance-id 4
```

Dates need a time zone (`Z` or `+01:00`) so a window is never scheduled in the wrong zone by accident.

| Action | Endpoint |
|---|---|
| List | `GET /api/status-pages/{id}/maintenances` |
| Schedule | `POST /api/status-pages/{id}/maintenances` |
| Show | `GET /api/status-pages/{id}/maintenances/{maintenance_id}` |
| Change | `PATCH /api/status-pages/{id}/maintenances/{maintenance_id}` |
| Cancel or end now | `DELETE /api/status-pages/{id}/maintenances/{maintenance_id}` |

## Password protection

A page can ask visitors for a password, for example a page only your customers should read. Set it under **Overview → Password**, or:

```bash
temps status-pages password set --id 1                       # prompts for it
printf '%s\n' "$PAGE_PASSWORD" | temps status-pages password set --id 1 --password-stdin
temps status-pages password set --id 1 --remove              # open the page again
temps status-pages password show --id 1
```

- Visitors see a password form. After the right password the browser keeps a signed cookie for 7 days; nothing is stored per visitor.
- While a password is set, the JSON at `…/summary.json` also needs the cookie and is not shared with other sites (no CORS header), the Atom feed is off, and subscribing needs the password. Confirmation and unsubscribe links in emails keep working, so nobody is stuck on a list.
- Setting, changing or removing the password signs every visitor out.
- Passwords are 8 to 256 characters and are stored only as an argon2 hash. Wrong passwords are limited to 5 per client per 15 minutes, and checking them never slows the rest of Temps down: a burst beyond what the server checks at once is asked to retry.

| Action | Endpoint |
|---|---|
| Show whether a password is set | `GET /api/status-pages/{id}/password` |
| Set, change or remove (`{"password": null}`) | `PUT /api/status-pages/{id}/password` |

## Webhooks

Post every public update of a page to your own HTTPS endpoint, e.g. a chat channel relay. Add one under **Notifications → Webhooks** or with the CLI. The **signing secret** is shown once, when the webhook is added; store it then. To change it, delete the webhook and add it again.

```bash
temps status-pages webhooks add --id 1 --url https://hooks.example.com/status   # prints the secret once
temps status-pages webhooks list --id 1
temps status-pages webhooks update --id 1 --webhook-id 2 --disable             # pause
temps status-pages webhooks remove --id 1 --webhook-id 2
```

Each event is a `POST` with a JSON body carrying only what the page shows:

```json
{
  "type": "incident_update",
  "page": { "title": "Example status" },
  "event": {
    "id": "3f9a…",
    "title": "Partial outage",
    "status": "identified",
    "message": "We found the cause and are rolling out a fix.",
    "affected_components": ["API"],
    "published_at": "2026-11-20T10:05:00Z",
    "starts_at": null,
    "ends_at": null
  }
}
```

`type` is `incident_update`, `incident_resolved` or `maintenance_scheduled` (which sets `starts_at` and `ends_at`). `event.id` is stable for an event, so use it to drop duplicates. The headers are `X-Temps-Event` (the type), `X-Temps-Event-Id` and `X-Temps-Signature: t=<unix seconds>,v1=<hex>`, where `v1` is the HMAC-SHA256, keyed with the secret, of `<t>.<raw body>`. Verify it before trusting a request, and reject old timestamps:

```js
import { createHmac, timingSafeEqual } from 'node:crypto'

function verify(secret, header, rawBody, toleranceSeconds = 300) {
  const match = /^t=(\d+),v1=([0-9a-f]{64})$/.exec(header ?? '')
  if (!match) return false
  const [, t, v1] = match
  if (Math.abs(Date.now() / 1000 - Number(t)) > toleranceSeconds) return false
  const expected = createHmac('sha256', secret).update(`${t}.${rawBody}`).digest()
  const given = Buffer.from(v1, 'hex')
  return given.length === expected.length && timingSafeEqual(given, expected)
}
```

**Delivery.** A background task checks every 20 seconds and delivers events published since the webhook was added (at most the last 24 hours). Any `2xx` answer counts as delivered. Otherwise Temps retries after 1 minute and then 10 minutes, and gives up after 3 attempts; the console and `webhooks list` show the last failure. Requests time out after 10 seconds, redirects are not followed, and the URL must be `https://` and resolve to a public address, checked again on every delivery. An event that stops being public before it is delivered (made private, the page unpublished) is not sent. Pausing a webhook drops the deliveries still waiting for it; after you resume it, public updates from the last 24 hours that it was never sent are delivered.

| Action | Endpoint |
|---|---|
| List | `GET /api/status-pages/{id}/webhooks` |
| Add (returns the secret once) | `POST /api/status-pages/{id}/webhooks` |
| Change the URL, pause or resume | `PATCH /api/status-pages/{id}/webhooks/{webhook_id}` |
| Delete | `DELETE /api/status-pages/{id}/webhooks/{webhook_id}` |

## Custom domains

A page can also be served on your own hostname, such as `status.example.com`. The hostname serves **only** the page (`/`), its JSON (`/summary.json`), its feed (`/feed.atom`), the password form (`/unlock`), and, when subscriptions are on, the subscribe form (`/subscribe`) and the confirmation and unsubscribe links; every other path answers "not found", and the hostname never reaches the Temps console, its API, or any application.

1. Open the status page and, under **Custom domains**, enter the hostname. Choose how to prove you control it:
   - **HTTP**: the hostname already points at this Temps instance.
   - **DNS TXT record**: prove control before moving traffic.
2. Create the DNS records Temps shows. That is always a record pointing the hostname at Temps: a `CNAME` to your public ingress or console hostname, or an `A` record to the server's address. With DNS verification, it also includes a `TXT` record at `_acme-challenge.<hostname>`.
3. Click **Verify**. Temps runs the same ACME flow it uses for every other certificate. Ownership is proven when the certificate is issued, and only then does the hostname start serving the page.

### Renewing the certificate

- **HTTP verification**: the certificate renews automatically within 30 days of expiry, like every other HTTP-01 certificate.
- **DNS verification**: the certificate is **not** renewed automatically, because every order needs a new `TXT` value. Temps notifies you 30 days before expiry, and the console shows the expiry date. Click **Renew**: Temps starts a new order and shows the new `_acme-challenge` record. Publish it, then click **Verify**.

The current certificate keeps serving while a renewal is in progress, and also when a renewal fails, until it expires. A failed renewal shows its error and a **Renew** button to try again. Only one verify or renew runs per hostname at a time; a second one started meanwhile is refused until the first finishes.

```bash
temps status-pages domains add --id 1 --hostname status.example.com          # HTTP verification
temps status-pages domains add --id 1 --hostname status.example.com --dns    # DNS TXT verification
temps status-pages domains verify --id 1 --domain-id 3
temps status-pages domains renew --id 1 --domain-id 3                         # new order; DNS: prints the new TXT record
temps status-pages domains list --id 1
temps status-pages domains remove --id 1 --domain-id 3
```

| Action | Endpoint |
|---|---|
| List | `GET /api/status-pages/{id}/domains` |
| Attach | `POST /api/status-pages/{id}/domains` |
| Verify | `POST /api/status-pages/{id}/domains/{domain_id}/verify` |
| Renew | `POST /api/status-pages/{id}/domains/{domain_id}/renew` |
| Remove | `DELETE /api/status-pages/{id}/domains/{domain_id}` |

A hostname cannot be attached if anything else on this instance uses it: an application, a project or environment domain, a custom route, the console or public ingress hostname, a name inside the preview or on-demand TLS zone, another status page, or a certificate already managed under **Domains**. Hostnames are compared after normalization (letter case, trailing dot, international names converted to punycode); wildcards and IP addresses are refused.

**Until a hostname is verified**, it serves nothing and no certificate is issued or presented for it. On-demand TLS never mints certificates for status-page hostnames.

**Taking it down.** Removing a hostname, unpublishing the page, or deleting the page makes the hostname answer "not found" immediately:

- Removing a hostname, or deleting the page, deletes its certificate (including the stored copy), which stops serving and renewal. The hostname keeps answering "not found" until it is attached again or used by an application.
- Unpublishing also releases the certificates. After publishing again, click **Verify** on each hostname.

Status-page hostnames are served by the control plane's proxy (single node, or `temps proxy` in a split control plane started with `--console-ingress-address`). Point them at the control plane, not at a worker node.

## Permissions and audit

Creating a page needs `status_page:create`; changing it, publishing, unpublishing, replacing its link or changing an incident update's visibility need `status_page:write`; deleting needs `status_page:delete`. On projects with team access these start at the project **admin** role, so viewers and deployers cannot publish anything.

Adding, verifying, renewing and removing custom domains, scheduling maintenance, setting the password and managing webhooks need `status_page:write`. Every change and every verification or renewal attempt is written to the audit log (`STATUS_PAGE_DOMAIN_ADDED`, `STATUS_PAGE_DOMAIN_VERIFIED`, `STATUS_PAGE_DOMAIN_VERIFICATION_ATTEMPTED`, `STATUS_PAGE_DOMAIN_RENEWAL_REQUESTED`, `STATUS_PAGE_DOMAIN_REMOVED`, `STATUS_PAGE_CREATED`, `STATUS_PAGE_UPDATED`, `STATUS_PAGE_PUBLISHED`, `STATUS_PAGE_UNPUBLISHED`, `STATUS_PAGE_URL_ROTATED`, `STATUS_PAGE_DELETED`, `STATUS_PAGE_INCIDENT_UPDATE_VISIBILITY_CHANGED`, `STATUS_PAGE_MAINTENANCE_SCHEDULED`, `STATUS_PAGE_MAINTENANCE_UPDATED`, `STATUS_PAGE_MAINTENANCE_CANCELLED`, `STATUS_PAGE_PASSWORD_SET`, `STATUS_PAGE_PASSWORD_REMOVED`, `STATUS_PAGE_WEBHOOK_CREATED`, `STATUS_PAGE_WEBHOOK_UPDATED`, `STATUS_PAGE_WEBHOOK_DELETED`), including the exact list of monitors selected when the selection changes.

## How it is served

- Public requests are answered from an in-memory snapshot. Viewing a page never runs a probe or a database query, so traffic to a status page — including someone guessing links — cannot slow Temps down. Only the subscribe form, confirmation and unsubscribe posts write to the database, and only for a published page that accepts subscriptions; they are limited to 10 requests per client per 10 minutes.
- Snapshots are rebuilt every minute, and immediately when you change or publish a page or an incident update's visibility.
- The link contains 128 random bits; it cannot be guessed or derived from any ID. Unknown, unpublished, deleted and replaced links all receive the same "not found" response.
- Requests are rate-limited per client (300 per minute per IPv4 address or IPv6 /64). Visitors that cannot be tracked individually during a flood share a separate budget, so a flood of addresses cannot lock out visitors already being served.
- The page asks search engines not to index it (`noindex`), so the link stays as private as you keep it.
- Pages are served on Temps' public-only routes (the same surface as webhook receivers), so they keep working when the console itself is restricted to an IP allowlist. The link uses your public ingress URL when one is configured, otherwise the external URL.

## Limits

- 100 status pages per instance, 50 monitors per page.
- Titles up to 120 characters, descriptions up to 1,000, public names and group names up to 80, incident update messages up to 5,000.
- 30 custom-domain verifications or renewals per page per hour, and 60 across the instance.
- Up to 5 custom domains per page.
- 10,000 subscribers per page, of which at most 1,000 waiting for confirmation.
- 20 scheduled or running maintenance windows per page, each at most 7 days long.
- 10 webhooks per page.
