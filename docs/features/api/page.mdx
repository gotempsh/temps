# API

Everything you can do in the Temps console goes through the same REST API, so anything you can click you can also script: create projects, deploy from CI, manage domains and environment variables, read logs and analytics. {{ className: 'lead' }}

---

## What you can automate {{ anchor: true, id: 'overview' }}

| Tool | Use it for |
|------|------------|
| REST API | Any integration. JSON over HTTPS under `https://<your-temps-host>/api/` |
| [Temps CLI](/docs/cli) (`bunx @temps-sdk/cli`) | Scripts and CI pipelines, without writing HTTP calls |
| [Node SDK](/docs/node-sdk) (`@temps-sdk/node-sdk`) | Typed API client for Node.js and TypeScript |
| [MCP server](/docs/mcp) | Letting AI assistants operate Temps |

The [REST API reference](/docs/api) lists the endpoints by area. This page covers authentication and the common automation tasks.

---

## Create an API key {{ anchor: true, id: 'api-keys' }}

API requests are authenticated with an API key. Create one in the console under **Settings → API Keys**. The key starts with `tk_` and is shown only once, so copy it into your secret store immediately. Temps keeps only a hash.

Each key has a role that decides what it can do:

| Role | Access |
|------|--------|
| `admin` | Everything |
| `platform_admin` | Users, settings and other platform administration; read-only on projects and deployments |
| `user` | Create and deploy projects, without platform administration |
| `reader` | Read-only access |
| `api_reader` | Read projects, deployments and analytics only |
| `custom` | Only the permissions you list, for example `deployments:create` and `deployments:read` |

You cannot give a key permissions you do not have yourself. `GET /api/api-keys/permissions` lists every permission name.

Keys expire after 365 days unless you choose another expiry. You can deactivate, reactivate and rotate them from the console or the API. If you have MFA enabled, the console asks you to verify again before it creates or rotates a key.

Server operators can also create a key from the shell of the Temps host, for example to bootstrap automation on a new instance:

```bash
TEMPS_DATABASE_URL=postgresql://... temps api-key --name ci-deploy --role user --expires-in-days 90
```

`temps api-key` defaults to the `admin` role. Pass `--role` (or `--permissions` with a `custom` role) to narrow it.

For more on roles and permission scopes, see [Manage team access](/docs/manage-team-access).

## Make a request {{ anchor: true, id: 'requests' }}

Send the key as a bearer token:

```bash
curl https://temps.example.com/api/projects \
  -H "Authorization: Bearer $TEMPS_API_KEY"
```

- **Format.** Requests and responses are JSON. Timestamps are ISO 8601 in UTC with a `Z` suffix.
- **Errors.** Errors use RFC 7807 Problem Details (`application/problem+json`) with a `title`, `status` and a `detail` that says what failed. See [Errors](/docs/errors).
- **Pagination.** List endpoints accept `page` (from 1) and `page_size` (default 20, maximum 100) and return a `total`. See [Pagination](/docs/pagination).
- **Rate limits.** Login, MFA verification, password reset and SSO endpoints accept 10 requests per minute per IP address and answer `429` with `Retry-After` beyond that.
- **Admin listener.** If the operator split the admin surface onto a private address ([Admin listener](/docs/admin-listener)), management endpoints are only reachable there.

## Explore the API {{ anchor: true, id: 'openapi' }}

Every instance serves its own OpenAPI document and an interactive Swagger UI, so the reference always matches the version you run:

| | Path |
|---|------|
| OpenAPI 3 document | `/api/api-docs/openapi.json` |
| Swagger UI | `/api/swagger-ui` |

Both require you to be logged in (or to send an API key), and both are served on the admin surface. You can generate a client for any language from the OpenAPI document. Temps' own console and CLI are generated from it.

## Compatibility and deprecation {{ anchor: true, id: 'compatibility' }}

### The 0.1.x promise

For **Stable** features, upgrades from one stable `0.1.x` release to a later
stable `0.1.x` release preserve the documented public interfaces below. This
promise starts at `0.1.0`; it does not cover `0.1.0-beta.*`, release candidates,
nightly builds, or undocumented internals. [Feature maturity](/docs/feature-maturity)
identifies the features covered by this promise. Beta and Experimental features
can change within `0.1.x`, with the notice process below.

| Surface | Preserved during stable 0.1.x upgrades | Compatible additions and limits |
|---------|--------------------------------------|---------------------------------|
| HTTP API | Documented methods and paths, accepted request fields, response field types, status codes, and documented behavior | New endpoints, optional request fields with backward-compatible defaults, and response fields may be added. Clients must ignore unknown response fields. New required inputs, removed fields, changed types, and new values in a closed documented enum are breaking changes. |
| CLI | Documented commands, flags, their meanings and defaults, exit-code behavior, and documented machine-readable output | New commands and optional flags may be added. Human-readable help, progress messages, and table formatting may change; use documented structured output for scripts. This applies to both the Rust `temps` binary and `@temps-sdk/cli`. |
| Configuration | Documented configuration keys, environment variables, accepted values, and defaults | New optional settings may be added. Existing valid configurations continue to work without newly required settings. Internal database tables and on-disk implementation details are not public configuration interfaces. |

Database migrations preserve platform data during supported forward upgrades.
This is not a promise that an older binary can run against a newer schema or
that a downgrade is safe. Back up before upgrading. Beta feature schemas may
be reshaped as described on the maturity page.

A security fix may need to reject previously accepted unsafe input or tighten
access. Such an exception must be identified in the release notes with the
impact and required operator action; it must not silently be presented as a
compatible change. Other regressions in Stable interfaces block a release.

### Deprecation and future 0.x changes

Deprecation means an interface still works but has a named replacement. For a
Stable interface, the first notice must ship in a stable release, in its
reference documentation, and in that release's GitHub release notes and
generated changelog. The notice must state the affected API path, CLI flag, or
configuration key; why it is deprecated; the replacement with a migration
example; and the earliest removal release and date.

Keep the deprecated interface working for the rest of `0.1.x`. Removal must
wait until a later `0.x` minor release, at least one stable patch release after
the notice and at least 30 days after that notice. For example, a flag deprecated
in `0.1.2` cannot be removed in `0.1.3`; it may be removed in `0.2.0` only after
both notice conditions have been met. The security exception above can shorten
this window when retaining the behavior would be unsafe.

For Beta and Experimental interfaces, changes or removal may happen within
`0.1.x`. Document the impact and migration in the changelog and release notes;
announce planned breaking changes in the target release's prerelease notes
before the stable release. Do not label these interfaces Stable merely to
imply compatibility.

Before any future `0.x` minor release with breaking changes, publish a migration
guide in the existing reference documentation and link it from the prerelease
and final GitHub release notes. List the old and new behavior, affected versions,
configuration or data migration steps, and any rollback limitations. Mark the
implementing commits as breaking changes so the generated changelog includes
them. A version change by itself is not sufficient notice. This policy makes
no compatibility promise across `0.x` minor releases or for a future `1.x`
series; those releases must publish their own policy.

### OpenAPI and SDK versions

Management routes use the unversioned `/api/*` base path. There is no general
`/api/v1` alias or API-version negotiation; individual protocol endpoints may
have their own versioned paths. The compatibility promise applies to the
interfaces themselves, regardless of the URL spelling.

OpenAPI has three separate version concepts:

- The top-level `openapi` field identifies the OpenAPI document format.
- `info.version` identifies the management API schema family. Its current
  `1.0.0` value is independent of the Temps binary version and does **not**
  promise Temps product `1.x` compatibility. Keep this schema family for
  compatible `0.1.x` changes; an incompatible management API revision in a
  future `0.x` minor release must change `info.version` and document the
  migration. It is not an exact schema fingerprint: additive changes and
  changes to Beta or Experimental features can occur within the family.
- The Temps release tag identifies the exact release's schema. Fetch
  `/api/api-docs/openapi.json` from the instance you target and record its
  Temps release alongside the saved spec. Do not infer the running server
  release or client compatibility from `info.version` alone.

The console client and the CLI's checked-in generated client are regenerated
from the matching backend source when its API surface changes. The CLI's
committed OpenAPI document is a release snapshot, not a spec for every server.
Generate custom clients from the target instance's authenticated OpenAPI
endpoint rather than from an unrelated checkout.

Published `@temps-sdk/*` packages have independent package versions; their
version numbers do not have to equal the Temps binary or OpenAPI version.
Pin the package version and use its release notes to select a version that
supports your server release. SDK releases that change the API client must
identify the source Temps release and supported server range in their release
notes; report compatibility only for combinations actually verified. During
SDK `0.x`, incompatible public SDK changes require a minor version increase
and migration notes, while compatible fixes and additions use patch versions.
Prerelease SDKs carry no stable compatibility promise. A newer SDK's newly
added method may require a newer server even when its older methods remain
compatible; upgrade the server before adopting that method. Pin both server
and SDK versions when depending on Beta or Experimental interfaces.

## Deploy from CI {{ anchor: true, id: 'ci' }}

There are two common patterns.

**Let Temps build from Git.** Trigger a build of a branch, tag or commit. The key needs the `projects:write` permission.

```bash
curl -X POST https://temps.example.com/api/projects/$PROJECT_ID/trigger-pipeline \
  -H "Authorization: Bearer $TEMPS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"branch": "main", "environment_id": '"$ENVIRONMENT_ID"'}'
```

**Build in CI and deploy the image.** Build and push the image in your pipeline, then tell Temps to deploy it. The key needs `deployments:create` on the project.

```bash
curl -X POST https://temps.example.com/api/projects/$PROJECT_ID/environments/$ENVIRONMENT_ID/deploy/image \
  -H "Authorization: Bearer $TEMPS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"image_ref": "ghcr.io/example/app:'"$GIT_SHA"'", "health_check_path": "/healthz"}'
```

The response (`202 Accepted`) contains the deployment `id`. Follow it with `GET /api/projects/{project_id}/deployments/{deployment_id}` until `status` reaches a final state, and read the job logs at `GET /api/projects/{project_id}/deployments/{deployment_id}/jobs`.

The CLI does the waiting for you:

```bash
bunx @temps-sdk/cli deploy:image --image ghcr.io/example/app:$GIT_SHA -p my-app -e production -y
```

You can also upload an image tarball or a static bundle without a registry. [Set up a CI/CD pipeline](/docs/set-up-ci-cd-pipeline) covers all of these, with a GitHub Actions example.

## Use the CLI {{ anchor: true, id: 'cli' }}

The CLI wraps the API for scripts and terminals:

```bash
bunx @temps-sdk/cli login                 # store a URL and API key on this machine
bunx @temps-sdk/cli projects list
bunx @temps-sdk/cli deployments logs -p my-app -f
```

In CI, configure it with environment variables instead of `login`:

| Variable | Purpose |
|----------|---------|
| `TEMPS_API_URL` | URL of your Temps instance |
| `TEMPS_TOKEN` | API key. `TEMPS_API_TOKEN` and `TEMPS_API_KEY` are also read, in that order |

Environment variables take precedence over a stored login. See the [CLI reference](/docs/cli) for every command.

## Call the API from your application {{ anchor: true, id: 'deployment-tokens' }}

Deployed applications do not need an API key. Temps injects two environment variables into every container:

| Variable | Value |
|----------|-------|
| `TEMPS_API_URL` | URL of the Temps API |
| `TEMPS_API_TOKEN` | A deployment token for the application's project |

Deployment tokens start with `dt_` and are bound to one project. The automatically generated token has full access to its project and does not expire. You can also create additional tokens with narrower permissions, and rotate or revoke tokens, under `/api/projects/{project_id}/deployment-tokens`.

## SDKs and MCP {{ anchor: true, id: 'sdks' }}

- [`@temps-sdk/node-sdk`](/docs/node-sdk) is a typed client for the whole API.
- `@temps-sdk/kv` and `@temps-sdk/blob` are clients for [KV](/docs/kv-storage) and blob storage.
- The browser analytics packages (`@temps-sdk/react-analytics` and others) are covered in [SDKs](/docs/sdks).
- The [MCP server](/docs/mcp) exposes Temps operations to AI assistants, using the same API keys and permissions.
