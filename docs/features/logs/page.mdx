# Logs & Debugging

Access real-time application logs, build logs, and deployment logs to debug issues quickly. Search, filter, and stream logs directly from the dashboard or via API. {{ className: 'lead' }}

---

## Structured telemetry from Sentry SDKs

Open **Projects → your project → Telemetry logs** to search structured application logs sent by an official Sentry SDK. These are the same native telemetry records queried by Temps' OpenTelemetry APIs. They are separate from container stdout, build logs and rrweb replay console events; a replay console breadcrumb does not automatically create a telemetry log.

For the verified Node 11.8.0 setup:

```javascript
import * as Sentry from '@sentry/node';

Sentry.init({
  dsn: process.env.TEMPS_SENTRY_DSN,
  enableLogs: true,
  dataCollection: { userInfo: false },
  sendClientReports: false,
});

Sentry.logger.info('Import completed', {
  'service.name': 'scheduled-worker',
  records: 42,
});
await Sentry.flush(5000);
```

Use `Sentry.logger`, or explicitly configure the SDK's console logging integration. Plain `console.log` alone is not this structured-log signal. In a browser, use only the public Temps DSN, never a server OTLP token. Avoid logging credentials, personal input values or full request bodies.

If no logs appear, confirm `enableLogs`, the selected project/time range and `service.name` filter, flush short-lived processes, then check the ingestion response and native log query. The [Sentry compatibility contract](/docs/error-tracking#sentry-compatibility) describes versions, typed-attribute preservation and partial-ingestion limits.

## Accessing Logs

### Via Dashboard

**Application Logs:**

1. Navigate to **Projects** → Select your project
2. Choose an **Environment**
3. Click on a **Container**
4. Open the **Logs** tab
5. View real-time logs or search historical logs

**Build Logs:**

1. Go to **Projects** → Select your project
2. Open **Deployments**
3. Click on a deployment
4. View build logs in the deployment details

**Deployment Logs:**

1. Navigate to **Deployments**
2. Select a deployment
3. View step-by-step deployment logs
4. See which steps succeeded or failed

### Via CLI

The CLI has three log commands. `runtime-logs` (alias `rlogs`) reads a running container, `deployments logs` reads a deployment's build and deploy steps, and `logs` searches collected logs across every project you can access.

```bash
# Last 100 lines from the production container of a project
temps runtime-logs --project my-project --environment production --tail 100

# Follow container logs in real time (Ctrl+C to stop)
temps rlogs -p my-project -e production -f

# Build and deploy step logs for a specific deployment
temps deployments logs --project my-project --deployment 123

# Search the last 6 hours of collected logs for errors in one project
temps logs search --project my-project --level ERROR --since 6h
```

If `runtime-logs` reports **No running containers found**, the environment has no live container: check `temps deployments list --project my-project` for a failed or stopped deployment. To read a container that belonged to a failed deployment, pass its ID with `--deployment`. If `logs search` returns nothing, run `temps logs capabilities` to check whether container logs are being collected.

### Via API

Live container logs are streamed over a **WebSocket**, not plain HTTP, so `curl` cannot read them. Use a WebSocket client and send your API key in the `Authorization` header:

```bash
# List the containers of an environment to get a container_id
curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/environments/{environment_id}/containers"

# Read the last 100 lines and close (follow=false), using websocat
websocat -H "Authorization: Bearer YOUR_TOKEN" \
  "wss://your-temps-instance.com/api/projects/{project_id}/environments/{environment_id}/containers/{container_id}/logs?tail=100&follow=false"
```

Build and deploy step logs are plain text, one file per deployment job:

```bash
# List the jobs (build, deploy, …) of a deployment to get a job_id
curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/deployments/{deployment_id}/jobs"

# Read the last 500 lines of one job's log
curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/deployments/{deployment_id}/jobs/{job_id}/logs?tail=500"
```

When a deployment is replaced, Temps saves the logs of its containers before removing them. List and read those saved logs with:

```bash
curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/deployments/{deployment_id}/container-logs"

curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/deployments/{deployment_id}/container-logs/{log_id}"
```

## Searching and Filtering Logs

### Search by Text

Use the search box in the logs viewer to find specific messages:

- **Exact match:** `"error connecting to database"`
- **Case-insensitive:** `ERROR` matches `error`, `Error`, `ERROR`
- **Partial match:** `database` finds all lines containing "database"

### Filter by Log Level

Filter logs to show only specific levels:

1. Click the **Filter** button in the logs viewer
2. Select log levels (Success, Info, Warning, Error)
3. View filtered results

### Filter by Time Range

View logs from specific time periods:

1. Use the **Time Range** selector
2. Choose:
   - Last hour
   - Last 24 hours
   - Last 7 days
   - Custom range
3. Logs update to show only the selected period

### Filter by Deployment

View logs for a specific deployment:

1. Go to **Deployments**
2. Select a deployment
3. View logs specific to that deployment
4. Compare logs across different deployments

## Real-Time Log Streaming

Stream logs in real-time to see events as they happen:

### In Dashboard

1. Open the **Logs** tab for a container
2. Click **Follow** or **Stream** button
3. Logs update automatically as new entries arrive
4. Scroll to bottom to see latest logs

### Via API

Container logs stream over a WebSocket. Each message is one log line as raw text. The stream stays open while `follow=true` (the default) and closes with code `1000` when it ends normally. Code `1011` means the stream failed after it started: the close reason says why. Do not parse the message payload to detect errors, because your application's own log lines can contain JSON with an `error` field.

Browsers cannot set the `Authorization` header on a WebSocket (the console uses its session cookie instead), so connect from a server-side runtime:

```javascript {{ title: 'Bun' }}
// Bun's built-in WebSocket accepts request headers.
const url =
  `wss://your-temps-instance.com/api/projects/${projectId}` +
  `/environments/${environmentId}/containers/${containerId}/logs?tail=100&follow=true`;

const socket = new WebSocket(url, {
  headers: { Authorization: `Bearer ${token}` },
});

socket.onmessage = (event) => console.log(String(event.data).trimEnd());
socket.onclose = (event) => {
  if (event.code !== 1000) {
    console.error(`Log stream closed (${event.code}): ${event.reason}`);
  }
};
```

```javascript {{ title: 'Node.js' }}
// Node's built-in WebSocket cannot send headers; use the `ws` package
// (npm install ws).
import WebSocket from "ws";

const url =
  `wss://your-temps-instance.com/api/projects/${projectId}` +
  `/environments/${environmentId}/containers/${containerId}/logs?tail=100&follow=true`;

const socket = new WebSocket(url, {
  headers: { Authorization: `Bearer ${token}` },
});

socket.on("message", (data) => console.log(data.toString().trimEnd()));
socket.on("close", (code, reason) => {
  if (code !== 1000) {
    console.error(`Log stream closed (${code}): ${reason.toString()}`);
  }
});
```

To stream a deployment's build log while it runs, connect to `/api/projects/{project_id}/deployments/{deployment_id}/jobs/{job_id}/logs/tail` the same way.

## Saved Searches

A saved search is a named set of log filters in one project: source, levels, environments, services, containers, nodes, a deployment, a text needle and attribute predicates, plus the time range it opens with. Any member who can read the project's logs sees its saved searches; creating, editing or deleting one needs `logs:write`. A project holds at most 100.

On the **Logs** page, filter by a service, then open **Saved searches** to save the current filters, pin a search to the top, reopen one, or start an alert from it. A search can hold filters the page has no control for (two levels, a container id). The page then says it is showing a wider view; alerts and dashboard tiles still apply every filter.

```bash
# Save the error lines of one service that mention a failed payment
temps logs saved create --project my-app --name "Payment failures" \
  --level ERROR --text "payment failed" --time-range 1h

temps logs saved list --project my-app
```

A saved search that an alert rule counts cannot be deleted; remove or change the rule first.

## Alerts on Logs

A log alert fires when the number of lines a saved search matches crosses a threshold, for example "payment failed" more than 20 times in five minutes. Create one from **Metrics → Alerts → New alert** by choosing **Log lines matching a saved search**, or from **Alert on this search** in the saved-search list.

A log alert is a metric alert rule whose series is a line count. It uses the same evaluator, alarm log, silencing and notification routes as every other metric alert. The evaluator counts matching lines once per evaluation over the trailing window; ingest never inspects lines against rules, so adding alerts adds no cost per log line.

- The window is at most one hour.
- The detector is a fixed threshold. Anomaly detection and per-series splits do not apply to line counts.
- A text needle is matched by scanning lines, and the scan stops at 1,000 matches or when its time budget runs out. The count is then a lower bound: it can show that more lines than the threshold matched, but not that fewer did, so a "fewer than" rule, or a "more than" rule still under its threshold, keeps its current state while the count is incomplete. An incomplete count never raises a false alarm and never resolves a real one.
- A log alert's filters are its saved search's; it takes no label filters of its own. Pointing an alert at another saved search starts it fresh and resolves the alarm the old search left open.

## Charting Logs on a Dashboard

A dashboard tile can chart a saved search instead of a metric. In the dashboard builder, set the tile's **Chart** to **A saved log search** and pick a value:

- **Matching lines** per bucket.
- **Average**, **sum**, **maximum**, **p50**, **p95**, **p99** or **distinct values** of a numeric attribute, such as `duration_ms`.

Counts come from the line index. A search with a text needle, or an install without a line index, is counted by scanning at most 5,000 lines, newest first; older buckets are left empty and the tile says from when it counted, so the chart never shows zero for a period nobody counted. A numeric attribute needs the line index and a search without a text needle. While some lines in the window are not indexed yet (the index fell behind and is catching up), counts are taken by scanning instead, and a numeric tile shows that it is unavailable rather than an average over part of the lines.

```bash
# Matching lines per 5 minutes over the last day
temps logs saved series 4 --project my-app --since 1d --bucket-secs 300

# p95 of a numeric attribute
temps logs saved series 4 --project my-app --metric p95:duration_ms
```

## Sending Logs from Outside Temps

A host, database, CDN or application that Temps did not deploy can send logs over HTTP as newline-delimited JSON, one object per line, to `POST /api/logs/ingest`. Vector and Fluent Bit both write this format, so syslog and log files reach Temps through a collector; Temps does not open a syslog port.

1. On the **Logs** page, filter by the service that should own the lines and choose **Send logs**, or run `temps logs keys create --project my-app --name web-01`.
2. Copy the key. It is shown once; Temps keeps only its hash.
3. Send lines with the key as a bearer token (`Authorization: Bearer tlk_…`) or in the `X-Temps-Log-Key` header.

The endpoint is a public receiver, like the webhook and OTLP receivers: it answers on the public ingress URL (**Settings → Public ingress**, which falls back to the console URL), and on a separate ingress listener when the console sits behind an IP allowlist. The **Send logs** dialog builds its snippets from that URL. Only the receiver is public; creating and revoking keys stays on the console.

```bash
curl -X POST https://temps.example.com/api/logs/ingest \
  -H "Authorization: Bearer $TEMPS_LOG_KEY" \
  -H "Content-Type: application/x-ndjson" \
  --data-binary $'{"level":"error","message":"payment failed","service":"checkout","order_id":42}\n'
```

A Vector sink:

```toml
[sinks.temps]
type = "http"
inputs = ["my_source"]
uri = "https://temps.example.com/api/logs/ingest"
method = "post"
encoding.codec = "json"
framing.method = "newline_delimited"
auth.strategy = "bearer"
auth.token = "${TEMPS_LOG_KEY}"
# Vector's default batch is larger than the endpoint accepts.
batch.max_bytes = 4000000
batch.max_events = 5000
```

Each line is read like a container's JSON line: `level` and `message` (or `msg`) as usual, other keys as attributes. The timestamp is read from `timestamp`, `@timestamp`, `time`, `ts` or `date` (RFC 3339 or an epoch number); a missing timestamp, or one more than 7 days old or 5 minutes ahead, becomes the arrival time. `service` (or `service.name`, `app`) names the service; without one, the key's default service applies. A key accepts at most 16 service names; further names fold into its default service.

| Limit | Value |
|---|---|
| Request body | 5 MiB |
| Lines per request | 10,000 |
| Bytes per line | 256 KiB |

A batch is parsed and charged to the budget whole before anything is stored: one malformed line refuses the batch with its line number, and a batch over the key's log ingestion budget is refused with `429` and `Retry-After` (each key is budgeted like one container: the per-container budget, or the project's override of it), so neither stores part of a batch. Refused lines are counted per key on the log pipeline status. A storage failure part-way through a batch (a full disk) stores the lines before it and fails the request; collectors deliver at least once and resend the batch, so those lines can appear twice. Revoking a key waits for its batches in flight, refuses its collectors from the next batch and closes its streams; lines already stored are kept.

## Structured Logging Best Practices

To get the most out of Temps logging, use structured logging in your application:

### JSON Logging

```javascript
// Node.js example
console.log(
  JSON.stringify({
    level: "info",
    message: "User logged in",
    userId: 123,
    timestamp: new Date().toISOString(),
  }),
);
```

```python
# Python example
import json
import logging

logging.info(json.dumps({
    'level': 'info',
    'message': 'User logged in',
    'user_id': 123,
    'timestamp': datetime.now().isoformat()
}))
```

### Log Levels

Use appropriate log levels:

```javascript
// Debug - detailed information for debugging
console.debug("Processing request", { requestId, userId });

// Info - general informational messages
console.info("User logged in", { userId });

// Warning - potential issues
console.warn("Rate limit approaching", { userId, requests: 95 });

// Error - errors that need attention
console.error("Database connection failed", { error: err.message });
```

### Include Context

Always include relevant context in logs:

```javascript
// Good: Includes context
console.log(
  JSON.stringify({
    level: "error",
    message: "Payment processing failed",
    userId: 123,
    orderId: 456,
    amount: 99.99,
    error: error.message,
    timestamp: new Date().toISOString(),
  }),
);

// Bad: Missing context
console.error("Payment failed");
```

## Downloading Logs

Save logs for offline analysis or archival:

### Via Dashboard

Logs saved from a replaced deployment's containers have a **Download** button. Open the deployment, find the saved container logs, and click **Download** to save them as a `.log` text file.

### Via API

There is no separate download endpoint. Save the response of the endpoints above to a file:

```bash
# A saved container log from a replaced deployment (JSON with the log content)
curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/deployments/{deployment_id}/container-logs/{log_id}" \
  -o container-log.json

# One deployment job's build or deploy log (plain text)
curl -H "Authorization: Bearer YOUR_TOKEN" \
  "https://your-temps-instance.com/api/projects/{project_id}/deployments/{deployment_id}/jobs/{job_id}/logs" \
  -o deployment-job.log
```

## Troubleshooting with Logs

<Properties>
  <Property name="Application Crashes">
    **Symptoms:** Container restarts, 502 errors **What to check:** 1. Look for
    error logs before restart 2. Check for out-of-memory errors 3. Review
    exception stack traces 4. Check for unhandled promise rejections (Node.js)
    **Example log pattern:** ``` ERROR: Unhandled exception TypeError: Cannot
    read property 'id' of undefined at /app/src/routes/users.js:45:12 ```
  </Property>

  <Property name="Slow Performance">
    **Symptoms:** High response times, timeouts **What to check:** 1. Search for
    "slow" or "timeout" in logs 2. Look for database query logs 3. Check for
    external API call delays 4. Review request processing times **Example log
    pattern:** ``` WARN: Database query took 5.2s INFO: External API call
    completed in 3.1s ```
  </Property>

  <Property name="Deployment Failures">
    **Symptoms:** Deployments failing to complete **What to check:** 1. Review
    build logs for compilation errors 2. Check for missing dependencies 3. Look
    for configuration errors 4. Review deployment step logs **Example log
    pattern:** ``` ERROR: Build failed npm ERR! code ELIFECYCLE npm ERR! errno 1
    npm ERR! build: `next build` ```
  </Property>

  <Property name="Connection Issues">
    **Symptoms:** Database or external service connection errors **What to
    check:** 1. Search for "connection" or "connect" errors 2. Look for timeout
    messages 3. Check for authentication failures 4. Review network-related
    errors **Example log pattern:** ``` ERROR: Failed to connect to database
    Error: connect ECONNREFUSED 127.0.0.1:5432 ```
  </Property>
</Properties>
