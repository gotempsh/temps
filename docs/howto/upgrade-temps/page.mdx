# Upgrade Temps

Temps includes a self-upgrade command that downloads the latest release from GitHub, verifies its checksum, and replaces the binary atomically. Database migrations run automatically on the next restart. {{ className: 'lead' }}

---

## Check your current version {{ anchor: true, id: 'check-your-current-version' }}

```bash
temps --version
```

Output:

```
v0.0.6 (abc1234) built 2026-03-04 12:34:56 UTC
```

---

## Check for updates {{ anchor: true, id: 'check-for-updates' }}

See if a newer version is available without installing it:

```bash
temps upgrade --check
```

Or use the health check command, which includes an update check along with other system diagnostics:

```bash
temps doctor
```

If a newer version exists, you will see:

```
WARN Update: v1.1.0 available - run 'temps upgrade' to update
```

## Upgrading to Projects and Services {{ anchor: true, id: 'upgrading-to-projects-and-services' }}

Read this before upgrading from a release that did not have Projects (groups of services). The upgrade itself is automatic; these are the changes you will notice.

- **Your apps are now called Services.** Every app you had is a service with the same slug, URLs, domains, deployments, variables and linked databases. Nothing moves and nothing is redeployed. See [Projects and Services](/docs/projects).
- **Projects are optional and start empty.** A Project groups services that ship together so they share a repository, variables and path routes. The upgrade does not create any; create one when you need it. See [Create a project and add services](/docs/create-a-project-and-add-services).
- **Additional templates with an unsupported preset are skipped.** If a template in a file passed with `temps serve --templates <file>` (or `TEMPS_ADDITIONAL_TEMPLATES`) uses a build preset this release no longer supports, the server logs a warning naming the template, its preset and the supported presets, and loads the rest instead of refusing to start. After restarting, check the logs for those warnings and fix the listed templates. A file that is missing or is not valid YAML still stops the server with an error.
- **Template kind `service` is now `app`.** Templates that say `kind: service` keep loading, but the API returns them as `app`. With CLI 0.1.36 or older, `templates list --kind service` returns nothing: upgrade the CLI (`bunx @temps-sdk/cli@latest`) and use `--kind app`.
- **Service template snapshots move to schema 3.** A service created from a service template (Keycloak, Browserless and others) keeps a copy of that template so it can be upgraded later. This release writes that copy in a new format (schema 3) when it creates or upgrades such a service, and still reads the old one. An older Temps binary cannot read schema 3, so **downgrading after this upgrade is not supported**. Take the backup below before you upgrade.

## Back up before upgrading {{ anchor: true, id: 'back-up-before-upgrading' }}

Before any upgrade, create a backup of your data:

**If you have S3 backup storage configured:**

Trigger a manual backup from the dashboard (**Settings > Backups > Run Backup**) or via the API.

**If you do not have S3 configured:**

At minimum, back up the Temps data directory and database:

```bash
# Back up the data directory (contains encryption key, auth secret, GeoLite2 DB)
cp -r ~/.temps ~/.temps-backup-$(date +%Y%m%d)

# Back up the PostgreSQL database
docker exec temps-timescaledb pg_dumpall -U postgres | gzip > temps-db-backup-$(date +%Y%m%d).sql.gz
```

<Note>
The `~/.temps/encryption_key` file is critical — it encrypts managed service credentials. If this file is lost, you cannot decrypt stored passwords. Always include it in your backups.
</Note>

## Run the upgrade {{ anchor: true, id: 'run-the-upgrade' }}

### Upgrade to the latest version

```bash
temps upgrade
```

If the binary is in a root-owned location (e.g. `/usr/local/bin/temps`):

```bash
sudo temps upgrade
```

The upgrade process:

1. Detects your platform (Linux/macOS, x86_64/ARM64)
2. Fetches the latest release from GitHub
3. Compares versions — exits if already up to date
4. Shows the upgrade plan (current version, target version, download size)
5. Asks for confirmation
6. Downloads the release tarball
7. Verifies the SHA-256 checksum (if available)
8. Replaces the binary atomically (write to temp file, then rename)

### Options

```bash
# Upgrade to a specific version
temps upgrade --version v1.1.0

# Skip the confirmation prompt
temps upgrade --yes

# Only consider stable releases (skip pre-releases)
temps upgrade --stable

# Upgrade a binary at a different path
temps upgrade --path /opt/temps/bin/temps
```

## Restart Temps {{ anchor: true, id: 'restart-temps' }}

The upgrade replaces the binary but does not restart the running process. You need to restart manually.

### If running under systemd (typical server setup)

```bash
sudo systemctl restart temps
```

If you run the proxy as a separate process:

```bash
sudo systemctl restart temps-proxy
```

### If running in a terminal

Stop the current process (Ctrl+C) and start it again:

```bash
temps serve
```

### Database migrations

Migrations run automatically when `temps serve` starts. There is no separate migration command. When the server boots, it:

1. Connects to PostgreSQL
2. Runs all pending migrations (120-second timeout)
3. Backfills any new TimescaleDB continuous aggregates
4. Starts serving traffic

If migrations fail, the server will not start. Check the logs for the specific migration error.

## Verify the upgrade {{ anchor: true, id: 'verify-the-upgrade' }}

After restarting:

```bash
# Check the version
temps --version

# Run diagnostics
temps doctor
```

The `doctor` command checks:

- Data directory integrity
- Encryption key presence
- Database connectivity and version
- TimescaleDB extension
- Migration count
- Docker daemon availability
- External connectivity (GitHub API, Docker Hub, Let's Encrypt)
- Git providers and DNS providers

If everything passes, your upgrade is complete. Visit the dashboard to confirm it loads correctly.
