## Flat Hostnames for Wildcard-TLS Providers

Temps generates preview hostnames from the platform preview domain — for
example `my-app-staging.example.com` under `example.com`. Compose services with
public ports also get generated hostnames; by default those use the
`service-environment.example.com` order (the **Standard** layout).

Some proxied DNS/TLS providers — including Cloudflare Universal SSL on free and
Pro plans — only cover the apex plus one wildcard label such as `*.example.com`.
They do not cover deeper hosts like `api.staging.example.com`. The **Flat**
hostname mode keeps generated service hostnames exactly one label beneath the
preview domain so a single-label wildcard cert covers them.

### Per-managed-zone configuration

The hostname mode is set **per managed zone**, where you configure the DNS
provider — not in global settings. Open **DNS Providers**, select your provider,
and for the managed zone toggle **Flat hostnames**. Providers
that benefit from flat hostnames (such as Cloudflare) surface and recommend the
option; others default to Standard.

Switching to Flat is an explicit, breaking change. Temps shows an impact preview
(the generated hostnames that change, plus any DNS records the sync would
reconcile) before you confirm. On apply, generated hostnames are recomputed and
routes reload; existing nested hostnames stop resolving. Custom domains are never
touched.

| Purpose | Standard | Flat |
| --- | --- | --- |
| Environment | `staging.example.com` | `staging.example.com` |
| Public compose service | `api-staging.example.com` | `staging-api.example.com` |

Generated DNS labels are sanitized and truncated to 63 characters with a stable
short-hash suffix when needed.

### DNS record sync

When you set a public **Edge target** in **Settings** and enable **Sync DNS
records** on a managed zone, Temps reconciles one proxied record per generated
hostname against the provider's zone — an `A`/`AAAA` record when the edge target
is an IP, otherwise a `CNAME`. Temps only updates or removes records that carry
its signed ownership marker; user-created records are left intact.

If the provider token cannot access the zone, Temps flags it on the managed
domain (and in the preview) and skips the sync rather than failing silently.

#### Records Temps does not manage

Temps never overwrites a DNS record it does not manage. When a generated
hostname already has such a record, the preview lists it as a conflict with the
reason, the record's current value and the value Temps would write. Choose one
option for each conflict:

- **Adopt** lets Temps take over that record: it is marked as Temps-managed and
  pointed at the edge target. Adopt is only offered for records nothing else in
  Temps manages. Records owned by custom domain delivery, the DNS records API or
  another Temps installation cannot be adopted.
- **Skip** leaves that hostname's record exactly as it is. Temps applies all
  other changes, and does not serve its self-signed origin certificate for the
  skipped hostname, because Temps does not manage its record.

A hostname with an `A`, `AAAA` or `CNAME` record Temps does not manage, of a
type other than the one Temps writes, is a conflict too: for example an `AAAA`
record when the edge target is an IPv4 address. While that other record
exists, the record Temps writes cannot be the hostname's only destination, so
these conflicts can only be skipped. To sync such a hostname, remove the other
record at the provider and preview again.

**Apply change** stays disabled until every conflict has a decision, and there
is no option to adopt all records at once. A decision covers the conflict as
the preview showed it. If the record, its owner, a record next to it or the
edge target changes after the preview, the apply changes nothing and asks you
to preview again. Adopting therefore never takes over a value you did not
review, and a skip never applies to a record you have not seen.

<Note>
**Upgrading from an earlier release.** Records created by the DNS sync of
earlier Temps releases carry no ownership marker, so the first sync after the
upgrade lists them as conflicts. Records that already point at the edge target
only need to be adopted, and their values do not change.
</Note>

## Request Timeouts

By default, the proxy applies **no timeout** to upstream app traffic —
regular HTTP requests, Server-Sent Events streams, and WebSocket connections
all stay open indefinitely (bounded only by TCP/OS-level limits). This is
deliberate: request timeouts are **opt-in**, so upgrading Temps, or deploying
an app with a slow endpoint or a long-lived connection, never breaks
something that worked before.

### Global defaults and the hard ceiling

Open **Settings → Request Timeouts** to configure platform-wide defaults:

| Setting | Default | Meaning |
| --- | --- | --- |
| Hard ceiling | 600s (10m) | The maximum any resolved timeout can be, once one is actually configured. Has no effect on traffic with no timeout at all. |
| Regular HTTP | 0 (no timeout) | Applies to non-streaming requests when a project/environment hasn't set its own override. |
| SSE idle | 0 (no timeout) | Applies to Server-Sent Events streams. Idle time only — an active stream is never cut off. |
| WebSocket idle | 0 (no timeout) | Applies to WebSocket connections. Idle time only. |

Setting any of the three defaults to a nonzero value opts the whole platform
into that timeout for every app that hasn't set its own override. The hard
ceiling always wins over whatever is resolved — globally or per
project/environment — but it never *creates* a timeout for traffic that
doesn't have one.

### Per-project and per-environment overrides

Under a project's **Environments → Environment settings**, the **Request
Timeouts** section lets you override any of the three values for that
specific environment:

- Leave a field blank to inherit the project default, then the global
  default (which is "no timeout" out of the box).
- Enter `0` to explicitly force "no timeout" for that environment — useful
  to opt one long-request app out even after an operator has configured a
  nonzero global default.
- Enter any other value to set an explicit timeout, always clamped to the
  operator's global hard ceiling.

The same three fields are available via the CLI:

```bash
bunx @temps-sdk/cli env timeouts <environment> --request 30 --sse-idle 900
bunx @temps-sdk/cli env timeouts <environment> --request 0   # force no timeout
bunx @temps-sdk/cli env timeouts <environment> --inherit      # clear all overrides
```
