# Upgrading Temps

An upgrade replaces the `temps` binary and then applies the new release's database migrations. Migrations run automatically the next time `temps serve` starts (or explicitly with `temps migrate`). Before they run, Temps backs up the database so the upgrade can be rolled back, and it refuses to run an older binary against a database that a newer release has already migrated. {{ className: 'lead' }}

---

## Before you upgrade

Check what you are running:

```bash
temps --version
temps upgrade --check   # is a newer release available on your channel?
```

Read the [release notes](https://github.com/gotempsh/temps/releases) for every version between yours and the target.

### What Temps backs up for you

When the new binary finds pending migrations on an existing database, it dumps the database **before applying any of them** to `<data dir>/backups/pre-migration/`. See [Automatic pre-migration backup](#automatic-pre-migration-backup) for what the dump contains. Nothing is backed up on a fresh install or on a normal restart with nothing to migrate.

### Stateless installations

The same backup requirement applies to a stateless control plane. Its local data directory may be temporary: copy the pre-migration dump to durable storage before replacing the container. If your database provider supplies backups, verify that you can restore one taken immediately before the upgrade, then explicitly use `--skip-pre-migration-backup` for that run. Temps does not infer that provider backups exist.

### What you still back up yourself

The pre-migration backup is the database only. Keep a copy of the data directory too — above all the encryption key, which decrypts every stored credential and cannot be regenerated:

```bash
# Installs made with deploy.sh keep their data in ~/.temps/data
cp -a ~/.temps/data ~/temps-data-backup-$(date +%Y%m%d)
```

If you configured S3 backup storage, also run a control-plane backup from **Settings > Backups** before a major upgrade: it is stored off the machine.

## Upgrade the binary

Use whichever method matches how you installed Temps.

### `temps upgrade` (self-upgrade)

```bash
temps upgrade            # newest release on your channel (stable by default)
sudo temps upgrade       # if the binary lives in a root-owned directory
```

It downloads the release for your platform, verifies its SHA-256 checksum, and atomically replaces the binary. It does **not** restart the running server — see [Restart Temps](#restart-temps).

```bash
temps upgrade --channel beta      # include beta pre-releases
temps upgrade --version v1.1.0    # a specific release (also how you go back to an older one)
temps upgrade --yes               # no confirmation prompt
temps upgrade --check             # only report whether an update is available
temps upgrade --path /opt/temps/bin/temps
```

`--stable` is a deprecated alias for `--channel stable`, which is already the default.

### From the console

When an update is available, the console shows a banner with an **Update now** action. It downloads the new binary, runs `temps migrate` with it (including the pre-migration backup), and restarts. Start the server with `--disable-self-update` to forbid this path.

### Upgrade script (`deploy.sh` installs)

```bash
curl -fsSL https://temps.sh/upgrade.sh | bash           # latest
curl -fsSL https://temps.sh/upgrade.sh | bash -s vX.Y.Z # a specific version
```

The script backs up the encryption key to `~/.temps/backups/pre-upgrade-<timestamp>/`, installs the new binary, upgrades Localup when tunnel mode is in use, restarts the services, and waits for a health check.

### Install script, Homebrew, or manual download

```bash
curl -fsSL https://temps.sh/install.sh | bash   # replaces ~/.temps/bin/temps
brew update && brew upgrade temps               # Homebrew (macOS)
```

### Docker Compose stack

Before changing any files, check where the running stack keeps its database:

```bash
PGVOL=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/var/lib/postgresql/data"}}{{.Name}}{{end}}{{end}}' temps-postgres)
docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' temps-postgres | grep -qx 'PGDATA=/home/postgres/pgdata/data' || PGVOL=
echo "${PGVOL:-not affected}"
```

If this prints `not affected`, continue with the steps below. If it prints a
volume name, such as `temps_postgres_data`, the stack was created from a Compose
file that mounted the volume at `/var/lib/postgresql/data`, while its PostgreSQL
image keeps its data in `/home/postgres/pgdata/data`. The database then exists
only inside the `temps-postgres` container, and `docker compose up` deletes it
when it replaces that container. In the same shell, stop the stack and copy the
database into the volume, keeping a private copy in your home directory:

```bash
docker stop temps-app temps-redis
(
  set -e
  umask 077
  docker stop --timeout 120 temps-postgres
  docker cp temps-postgres:/home/postgres/pgdata/data - > "$HOME/temps-pgdata-backup.tar"
  docker run --rm -i --user root --entrypoint sh \
    -v "$PGVOL":/home/postgres/pgdata/data gotempsh/timescaledb-walg:pg18 -c \
    'if [ -n "$(ls -A /home/postgres/pgdata/data)" ]; then echo "volume is not empty" >&2; exit 1; fi
     tar -x -C /home/postgres/pgdata' < "$HOME/temps-pgdata-backup.tar"
  echo "database copied into $PGVOL"
)
```

Continue only if the last line is `database copied into` followed by the volume
name. If a command fails, the `temps-postgres` container still holds the
database, so do not run `docker compose up` until the copy succeeds.
`temps-pgdata-backup.tar` is a complete copy of the database that only your
account can read. Keep it until the upgraded console shows your projects.

If the copy stops with `volume is not empty`, the volume holds an older cluster
from a previous PostgreSQL image that this stack no longer uses. Save it and
empty the volume, then run the previous commands again:

```bash
(
  set -e
  umask 077
  docker run --rm -v "$PGVOL":/volume alpine:3.22 tar -cf - -C /volume . > "$HOME/temps-postgres-volume-old.tar"
  docker run --rm -v "$PGVOL":/volume alpine:3.22 find /volume -mindepth 1 -delete
)
```

Back up the `postgres_data` volume, create a private `.env` with
`install -m 600 .env.example .env`, and set new, independent hexadecimal values
for `POSTGRES_PASSWORD` and `CLICKHOUSE_PASSWORD`. Keep the
file owned by the account that operates Temps and mode `0600`; it grants access
to the loopback-published data services. Existing stacks upgrading to the
ClickHouse-enabled Compose file must add `CLICKHOUSE_PASSWORD` before running
`docker compose up`.
Set `TEMPS_ADMIN_EMAIL` to the administrator email; it is used only when the
database has no existing user.
Set `TEMPS_ADMIN_PASSWORD_FILE` to a permission-restricted password file. For a
new file that satisfies the password policy:

```bash
mkdir -p secrets
chmod 700 secrets
{ printf 'tT3!'; openssl rand -hex 32; } > secrets/admin_password
{ printf 'iI4!'; openssl rand -hex 32; } > secrets/admin_ingress_password
chmod 444 secrets/admin_password secrets/admin_ingress_password
```
Set `TEMPS_ADMIN_INGRESS_PASSWORD_FILE` to the second file. It protects the
loopback-only admin port (`127.0.0.1:9001`) with username `temps`; keep it
independent from the Temps account password. The file must contain one non-blank
line of 16–72 printable ASCII bytes or the ingress fails closed. The public ingest
listener remains on `127.0.0.1:9000` and does not serve admin routes. The updated stack uses
separate public and admin proxy containers: only the public proxy joins the
managed-workload network, and both continue to publish exclusively on host
loopback.
Set `DOCKER_GID` to the group that owns `/var/run/docker.sock` as seen inside a
container on Linux or macOS:

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock alpine:3.22 stat -c '%g' /var/run/docker.sock
```
Then rebuild and start the stack normally:

```bash
docker compose up --build --detach --remove-orphans
```

The one-shot `postgres-credential-sync` service connects over the private Unix
socket and rotates the existing `temps` role to the configured SCRAM password
before the application starts. The authenticated PostgreSQL health check keeps
Temps stopped if rotation did not succeed. ClickHouse starts with its own
authenticated `temps` user and persistent volume before the application starts.
The former global Redis service can be removed; it was not a Temps control-plane
dependency. `--remove-orphans` removes its old container; the `redis_data`
volume is retained so deletion remains an explicit operator decision. The
optional KV feature manages its own Redis instance.

To roll back Temps, preserve the hardened `docker-compose.yml`, `Dockerfile`,
`.dockerignore`, `.env`, and admin-password secret file, check out the previous
application source, restore those files (including the separate admin-ingress
password secret), and rebuild. The hardened Dockerfile builds the binary
inside its Alpine stage; older Dockerfiles expected a separately built host
binary and are not compatible with this Compose workflow. Do not restore the
old Compose file: it contains the retired known database password and will no
longer match the rotated role. If the credential sync fails, inspect it before
retrying:

```bash
docker compose logs postgres postgres-credential-sync
docker compose run --rm postgres-credential-sync
```

## Apply database migrations

Pick one of the two:

- **Automatically on start (default).** `temps serve` applies pending migrations before it starts serving. Simple, and right for most single-node installs.
- **Explicitly with `temps migrate` (recommended for large databases).** Run the *new* binary's `migrate` command, watch it finish, then restart the server. A slow migration can then never hold the server in a restart loop.

```bash
TEMPS_DATABASE_URL=postgresql://... temps migrate --dry-run   # show the plan, change nothing
TEMPS_DATABASE_URL=postgresql://... temps migrate             # back up, then apply (asks first on a terminal)
TEMPS_DATABASE_URL=postgresql://... temps migrate --yes       # no prompt
```

Pass `--data-dir` (or set `TEMPS_DATA_DIR`) if your data directory is not `~/.temps`; that is where the pre-migration backup goes.

Each startup, in order:

1. **Schema guard.** Temps compares the migrations recorded in the database with the ones it knows. If the database has migrations this binary does not know — it was migrated by a newer release — Temps refuses to start and changes nothing. See [Database schema is newer than this binary](#database-schema-is-newer-than-this-binary).
2. **Pre-migration backup**, only if there are pending migrations on an existing database. See below.
3. **Migrations.** Each runs in its own transaction; a statement waiting more than 15 seconds for a lock fails fast, and the whole step is bounded at 10 minutes. If a migration fails, the server does not start and the database stays at the last migration that succeeded.
4. **Maintenance** that does not block startup (large concurrent index builds, analytics backfills) runs in the background once the server is up.

Migrations are idempotent: starting the same version again is a no-op.

### Automatic pre-migration backup {{ anchor: true, id: 'automatic-pre-migration-backup' }}

| | |
|---|---|
| **When** | Pending migrations on a database that already has applied ones. Never on a fresh install or a restart with nothing to migrate. |
| **Where** | `<data dir>/backups/pre-migration/` — `~/.temps/data/backups/pre-migration/` for `deploy.sh` installs. The directory is readable only by the Temps user. |
| **Files** | `temps-pre-migration-<UTC time>-<new version>.dump` (a `pg_dump` custom-format archive, compressed) and a `.json` manifest with the release it came from (`previous_version`), the migrations about to run and the tables dumped without data. |
| **Retention** | The newest 3 backups; older ones are deleted. |
| **Contents** | Every table's schema, and the data of everything except high-volume telemetry (proxy logs, traces, metrics, log events, analytics, session replays, error events, uptime samples, AI usage logs), which is dumped schema-only. This is the same scope as the control-plane backup, and it keeps an upgrade of a busy instance from waiting on gigabytes of telemetry. |
| **How** | A `pg_dump` on the `PATH` that is at least as new as the PostgreSQL server; otherwise a one-shot `postgres:<server major>` container on the host network, the same way control-plane backups run. |

The log line `Pre-migration database backup written to …` gives the exact path.

**If the backup fails, nothing is migrated** and Temps exits with the reason (for example, no suitable `pg_dump` and no reachable Docker daemon). Fix the cause and start again. If you cannot, take your own backup and start **once** with the opt-out flag:

```bash
temps serve --skip-pre-migration-backup ...     # or: temps migrate --skip-pre-migration-backup
```

The opt-out is a command-line flag on purpose — not an environment variable — so it cannot stay switched on for later upgrades. Remove it after that start.

Stateless control planes have the same backup requirement. Their data directory may be temporary, so retain the dump in durable storage or explicitly skip it only after verifying a database-provider backup. See [Stateless installations](#stateless-installations).

<Note>
Rolling back with this backup restores the configuration as it was at upgrade time. Telemetry recorded before the upgrade (logs, traces, analytics) is not in it. If you need to keep telemetry across a rollback, take a full `pg_dump` or a volume snapshot before upgrading.
</Note>

## Restart Temps {{ anchor: true, id: 'restart-temps' }}

<CodeGroup>

```bash {{ title: 'Linux (systemd)' }}
sudo systemctl restart temps
```

```bash {{ title: 'macOS (launchd)' }}
launchctl kickstart -k gui/$(id -u)/dev.temps.temps
```

</CodeGroup>

In a split topology, restart the console (`temps serve --role=console`) and then the separate proxy service (`sudo systemctl restart temps-proxy`). Run `temps upgrade --split` to print these steps for your install. In a terminal, stop `temps serve` with Ctrl+C and start it again.

## Verify the upgrade

```bash
temps --version
curl -fsS http://127.0.0.1:<console port>/healthz   # liveness
curl -fsS http://127.0.0.1:<console port>/readyz    # ready to serve
temps doctor                                        # data dir, encryption key, database, migrations, Docker, connectivity
sudo systemctl status temps                         # Linux
launchctl list dev.temps.temps                      # macOS
```

Open the console and check that your projects, environments and services are listed.

## Roll back an upgrade {{ anchor: true, id: 'roll-back-an-upgrade' }}

Migrations only go forward. To return to the previous release you need **both** the previous binary **and** the database as it was before the upgrade. Starting only the old binary on the upgraded database does not work: the schema guard (and, in older releases, the migrator) refuses it, so that an older binary cannot write to a schema it does not understand.

The example below is for a `deploy.sh` install (database container `temps-timescaledb`, user and database `temps`, data in `~/.temps/data`). Adjust names to your setup.

1. **Stop every Temps process connected to this database**, including standalone proxies and other console nodes. Keep them stopped until restore completes.

   ```bash
   sudo systemctl stop temps
   # Split deploy.sh installations also have this service:
   sudo systemctl stop temps-proxy
   # On macOS, stop the corresponding launchctl jobs.
   ```

2. **Pick the backup and the version to return to.** The newest backup was taken by the upgrade you are undoing; its manifest names the release that ran before it.

   ```bash
   BACKUP=$(ls -1t ~/.temps/data/backups/pre-migration/temps-pre-migration-*.dump | head -n1)
   echo "$BACKUP"
   jq -r .previous_version "${BACKUP%.dump}.json"
   ```

3. **Install that release's binary.**

   ```bash
   temps upgrade --version vX.Y.Z --yes
   ```

4. **Restore the database into a fresh one**, keeping the upgraded database aside in case you need it:

   ```bash
   docker exec temps-timescaledb psql -v ON_ERROR_STOP=1 -U temps -d postgres \
     -c 'ALTER DATABASE temps WITH ALLOW_CONNECTIONS false' \
     -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'temps' AND pid <> pg_backend_pid()" \
     -c 'ALTER DATABASE temps RENAME TO temps_before_rollback' \
     -c 'CREATE DATABASE temps OWNER temps'
   docker exec temps-timescaledb psql -v ON_ERROR_STOP=1 -U temps -d temps \
     -c 'CREATE EXTENSION IF NOT EXISTS timescaledb' \
     -c 'SELECT timescaledb_pre_restore()'
   docker exec -i temps-timescaledb pg_restore --no-owner --exit-on-error \
     -U temps -d temps < "$BACKUP"
   docker exec temps-timescaledb psql -v ON_ERROR_STOP=1 -U temps -d temps -c 'SELECT timescaledb_post_restore()'
   ```

5. **Start Temps** and [verify](#verify-the-upgrade). Once you are satisfied, drop the set-aside database: `docker exec temps-timescaledb psql -U temps -d postgres -c 'DROP DATABASE temps_before_rollback'`.

If you upgraded with `--skip-pre-migration-backup`, restore the backup you took yourself in step 4 instead.

## Upgrading the database

TimescaleDB runs as a Docker container and is upgraded independently of Temps:

```bash
docker pull timescale/timescaledb-ha:pg18
docker stop temps-timescaledb
docker rm temps-timescaledb

docker run -d \
  --name temps-timescaledb \
  --restart unless-stopped \
  -e POSTGRES_USER=temps \
  -e POSTGRES_PASSWORD="YOUR_DB_PASSWORD" \
  -e POSTGRES_DB=temps \
  -p 127.0.0.1:5432:5432 \
  -v temps-db-data:/home/postgres/pgdata/data \
  timescale/timescaledb-ha:pg18

sudo systemctl restart temps
```

The data persists in the `temps-db-data` volume. If you used the deploy script, the database password is in `~/.temps/.wizard-state/db_password`.

## Troubleshooting

### Database schema is newer than this binary {{ anchor: true, id: 'database-schema-is-newer-than-this-binary' }}

```text
The database schema is newer than this Temps binary (v…): N applied migration(s) are unknown to it: m2026…
```

A newer release migrated this database, then an older binary was started on it — usually after rolling back only the binary. Nothing was changed. Either start the newer release again (`temps upgrade --version <that release>`), or [roll back](#roll-back-an-upgrade) properly by restoring the pre-migration backup.

### Pre-migration backup failed

```text
Refusing to apply N pending database migration(s) because the automatic pre-migration backup failed: …
```

Nothing was changed. Common causes:

- **No usable `pg_dump`.** Install the client tools for your PostgreSQL major version (`postgresql-client-18`), or make the Docker daemon reachable so Temps can use a `postgres:18` container.
- **The data directory is not writable** by the Temps user, or the disk is full.

If you cannot fix it now, back up the database yourself and start once with `--skip-pre-migration-backup`.

### Migration errors

The log names the migration that failed and why; the database stays at the last migration that succeeded. Check that the database is reachable and healthy, fix the cause, and start again (or run `temps migrate` to watch each step):

```bash
docker exec temps-timescaledb pg_isready -U temps
docker logs temps-timescaledb --tail 50
```

A migration that times out on a large database is safest applied with `temps migrate` while the server is stopped.

### Service fails to start

```bash
sudo journalctl -u temps -n 100 --no-pager   # Linux
tail -100 ~/.temps/logs/temps.log            # macOS
```

Check that the data directory and encryption key are readable only by the Temps user (`chmod 700 ~/.temps/data`, `chmod 600 ~/.temps/data/encryption_key`).
